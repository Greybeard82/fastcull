## Not measurable yet

These are PRD 3.5 budgets with no number, because the feature they measure does not
exist. None of them was approximated by timing something adjacent.

| Metric | PRD budget | Why there is no number |
| :--- | :--- | :--- |
| Next/previous, cache hit | < 16 ms | PRD 3.3's prefetch window and LRU cache do not exist - not in any form, in any session so far. There is no cache, therefore no cache-hit code path to time. Timing a second decode of a bitmap that happens to still be in memory would not be measuring this metric, it would be measuring a thing the app never does. Blocked on PRD 3.3. |
| Enter zoom, Tier A cached | < 50 ms | Zoom mode does not exist (PRD 1.7, scheduled v0.2). Nothing to enter, nothing to time. |
| Enter zoom, Tier B | < 400 ms CPU / < 100 ms GPU | Zoom mode does not exist (v0.2), and there is additionally no debayer implementation at all for the Tier B path to use - see PRD 3.4's open gap. |
| Pan at 1:1 | sustained 60 fps | Zoom mode does not exist (v0.2). A frame-rate measurement also needs a compositor and a real window, which a headless harness does not have. |

## How to read this

- **Real vs. synthetic file counts.** The real corpus is 100 files. The two budgets
  PRD 3.5 defines at "2,000 files" are measured against a synthetic corpus of 2,000
  NTFS hard links cycling over those 100 files — **2,000 real photos were not used**.
  Hard links are genuine directory entries over the real bytes, so enumeration,
  `FileInfo.Length` and header parsing all do real work, but 2,000 entries share 100
  extents, so the OS page cache is warmer than it would be for 2,000 distinct files.
  That biases scan and decode timings **optimistically**. The "real corpus (control)"
  row exists to bound that bias: compare its ms/file against the synthetic one.
- **Every timing here is warm-cache.** The harness scans the corpus once to build
  its fixture sets before it measures anything, so the OS page cache is already hot
  by the time the scan is timed. A genuinely cold first-open of a 2,000-file folder
  off NVMe is **not** measured by this run and will be slower — possibly much
  slower. Read the scan and first-image rows as a floor, not as the number a user
  sees when they open a card for the first time.
- **"First image" is a proxy.** It measures folder-open to the first decoded
  thumbnail — pixels in hand, not pixels lit. It stops before the XAML
  `SoftwareBitmapSource` marshal, previously measured at roughly 30 ms, negligible
  against a 1.5 s budget.
- **The rating row is decision latency**, not end-to-end. `PropertyChanged` is raised
  in `FilmstripItemViewModel`, which lives in the WinUI project and cannot be
  constructed headlessly; the compositor repaint after it is GPU-scheduled and not
  the app's to time.
- **No BenchmarkDotNet.** PRD 3.5 wants a regression gate that runs routinely, not a
  statistically rigorous micro-benchmark suite with warm-up iterations taking minutes
  per run. A `Stopwatch` harness running the real pipeline against the PRD's absolute
  budgets fits PRD 5's architecture (`Benchmarks/PerfHarness.cs`) and this project's
  no-new-packages default. The tradeoff is real and worth naming: single-run timings
  are noisier than a proper harness would produce, so treat a change under about 25%
  as noise — which is, conveniently, exactly the threshold PRD 3.5 sets.
