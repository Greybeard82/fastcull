## Task B — rotation

### How it is rendered, and why this way

Three things had to be true at once: the photo turns, it stays inside its cell at the shared
height uncropped, and the tick and weight bar match its *rendered* width.

**The layout box and the image are sized separately.** A `frame` takes the post-rotation box —
shared height tall, width from the rotated aspect — and that is what participates in layout and
what the tick and bar measure against. The `Image` inside is laid out **pre-rotation** (width and
height swapped on a quarter turn) and turned about its centre, so its bounding box lands exactly
on the frame.

Two alternatives from B.3, and why not:

- **`RenderTransform` alone** draws the photo rotated while it still *occupies* its unrotated box.
  Neighbours overlap and the bars size to the wrong width. Rejected on that basis — the transform
  is still used, but only inside a frame that already has the right shape.
- **Re-decoding to bake in the rotation** would spend a decode on a transform, blow the §3.5
  keypress budget, and invalidate cache entries once §3.3 lands. Explicitly forbidden, and now
  written into the PRD.

**One thing I got wrong first and had to measure.** The image initially sat in a `Grid`. WinUI
clamps a child's `DesiredSize` to the space available, so at 90° the image's swapped width was
cut down to the frame's much narrower width — measured, it rendered **206×204 instead of
206×311**, while its unrotated neighbour was 326 tall. A `Canvas` is the only panel that measures
children unconstrained, so the image moved into one and is positioned explicitly. The thumbnails
had the identical bug inside their fixed slot and got the identical fix.

### The aspect trap

`EffectiveAspectRatio` on the item ViewModel inverts on a quarter turn, and that is what feeds
the equal-height rule. `StageLayout` itself is unchanged — it already handled mixed aspects, it
just needed to be told the truth. A consequence worth knowing: **rotating one photo can resize
its two neighbours**, because the rule sizes to the widest photo visible.

### Keys

`A` = clockwise, `S` = counter-clockwise, both resolved before the extended-key/numpad split.
Both were genuinely unmapped beforehand — checked, not taken on faith; `VirtualKey.A` was in fact
asserted as unmapped by an existing test, which I moved rather than deleted. There is now a test
named `A_IsClockwise_And_S_IsCounterClockwise_DeliberatelyNotSwapped` so that anyone "fixing" the
apparent transposition has to delete a test that tells them not to.

### Buttons

In the centre slot's caption row, right-aligned, flat and borderless, acting on the **active**
item rather than slot 1's item. Verified at the boundary: with photo 1 active in the *left* slot,
the buttons rotate the left photo.

**They were changing the selection.** A tap on a button bubbled to the slot's own `Tapped`
handler, so rotating also selected slot 1 — measured, the counter moved `1/100` → `2/100`.
Rotation must move nothing; the tap is now handled before it reaches the slot.

**PRD 1.10 in every visual state, checked rather than assumed.** The stock WinUI `Button` paints
near-black greys on hover and press, so the buttons use a custom template that paints no
background in any state. Measured at rest, on hover and while pressed: the same 39 non-black
pixels in the button box each time — only the glyph strokes — differing solely in brightness
(luminance 8089 → 10750 from hover to pressed), with padding, gaps and corners at exactly
`#FF000000`.

## Task C — persistence

Rotation takes exactly the route ratings take: non-blocking `TryWrite`, same channel, same
background writer, same 250 ms / 32-op batching, same `ConfigureAwait(false)`.

### The migration

`CREATE TABLE IF NOT EXISTS` is a no-op against an existing database, so the column was added to
that statement *and* a real migration added.

**Tested against a pre-existing database, not only a fresh one** — this is the test the work order
predicted would be skipped. `PreExistingDatabaseWithoutTheRotationColumn_IsMigratedOnOpen` builds
a database with the previous schema (no rotation column) carrying an already-rated photo, opens it
through `SessionStore`, and asserts the column is added, the old rating survives, and the write
that would previously have thrown `no such column: rotation` now works.

One correction to the work order's suggested approach: it proposed keying the migration on
`PRAGMA user_version`. **Version alone is wrong** — a freshly created database already has the
column from `CREATE TABLE` while its `user_version` is still 0, so a version-only check would try
to add a column that already exists and throw. The guard reads `PRAGMA table_info`; `user_version`
is still recorded for future revisions.

### The clobbering bug I had to design around

The writer collapses pending writes by path. A naively widened record would mean a rating write
and a rotation write for the same photo in one batch overwrite each other, and whichever landed
second would silently reset the other. Writes therefore carry only the fields they set, merge on
collapse, and apply with `COALESCE`. There is a test for exactly that collision.

`LoadRatingsAsync` became `LoadPhotoStatesAsync`, returning one record per photo rather than a
second parallel dictionary — the work order was right that two dictionaries keyed by path is a
bug waiting to happen.

### The real close-and-reopen result

Not just tests. Rotated four photos through the UI, closed the app completely with the title-bar
X, reopened it on the same folder. Read back **from the database directly**:

```
schema  : 1
_MG_4175.jpg   flag=Picked    stars=5  rotation=1 (90deg)
_MG_4201.jpg   flag=Unflagged stars=0  rotation=2 (180deg)
_MG_4211.jpg   flag=Unflagged stars=0  rotation=3 (270deg)
_MG_4252.jpg   flag=Unflagged stars=0  rotation=1 (90deg)
```

All three of 90°, 180° and 270° present, so a sign error or modulo bug had nowhere to hide. On
reopening, the stage showed exactly those orientations, thumbnails included. `_MG_4175` kept its
Picked/5★ rating alongside its rotation, confirming the two fields do not disturb each other
through a real round trip.

The final rotation was made shortly before clicking X and still landed, and the process exited
cleanly in ~1s every time — so the cancelable `AppWindow.Closing` flush (`dd946e0`) covers
rotation as it does ratings.

## Task E — EXIF orientation: the work order's premise was wrong

The work order states: *"There is no EXIF orientation handling anywhere in this codebase. Grep
confirms it."* **It is there.** `ThumbnailService` passes `ExifOrientationMode.RespectExifOrientation`
to `GetSoftwareBitmapAsync` — a grep for `Orientation` returns exactly that line.

What that means in practice, measured rather than reasoned:

**1. JPEG and friends: orientation IS applied.** I built a JPEG tagged `Orientation = 6` and put
it through the app's own decode path. Stored pixels 1000×667; the app returned **640×960**, axes
swapped. So `MetadataExtractor` is not even needed for this path — WIC does it.

**2. RAW: orientation is NOT applied.** The RAW path hands WIC an *embedded JPEG preview*, and
those previews carry **no orientation tag of their own** — verified across `.ARW` and `.CR2`, at
every preview size (`ownOrientation=(absent)` in all cases). The RAW container's own tag is never
read. So `RespectExifOrientation` is honoured, but there is nothing in the stream to honour.

**3. Behaviour is therefore inconsistent between formats — the worst case the work order named.**
A portrait JPEG displays upright; a portrait RAW displays as the preview was stored. Under Paired
mode (PRD 1.4) the same frame can display differently depending on which file is the display
source.

**What I could not determine:** whether a camera writes a portrait RAW's embedded preview
already-rotated. If it does, RAW is accidentally fine and there is much less to fix. The sample
corpus is 100% landscape at orientation 1, so this needs one real portrait `.ARW` to settle. That
is the single most useful thing to check before building anything here.

### Does the delta framing protect stored rotations? Partly — and the gap is worth naming

The work order asked me to say so loudly if it does not, so: **it does not fully.**

A delta is relative to a baseline. If the RAW baseline is corrected later, then for a RAW file
whose EXIF orientation is not 1:

- **Never manually rotated (delta 0)** → unaffected, and starts displaying correctly. This is the
  desired outcome and covers the overwhelming majority.
- **Already manually rotated** → the correction applies *on top of* the user's, and the photo
  becomes double-rotated.

So the at-risk set is precisely *RAW files with non-1 EXIF orientation that the user has already
rotated by hand*. **That set is empty today** — the feature just shipped and the corpus has no
such file. It stops being empty the first time you cull a portrait RAW shoot and straighten some
of them.

Storing an absolute orientation instead would **not** have been safer; it trades this problem for
a worse one, because then even untouched photos could never benefit from a later fix.

**If you want this closed cheaply:** store the decode-time baseline beside the delta — one extra
`INTEGER` column — so a later change can reconcile the two. That is an afternoon now and a data
migration over thousands of hand-rotated photos later. Both risks are recorded in PRD §7; I have
not built either, per the work order.

`A`/`S` were verified only through `InputRouter` unit tests and the buttons were driven by mouse.
The work order specifically asked me to re-test that arrow keys, `Z`/`X`/`C` and the number keys
still work after clicking a rotate button — **I could not do that with real keys.** What I can say:

- The buttons are `IsTabStop="False"` and focus is handed back to the filmstrip explicitly on
  click.
- Keyboard is owned by `RootGrid_PreviewKeyDown`, which *tunnels from the root down* and so fires
  wherever focus sits — structurally, a focused child cannot pre-empt it.
- Pointer routing definitely survives: after clicking rotate buttons, clicking a thumbnail still
  navigates (counter moved to `5/100`).

That is a strong argument, not a test. **Please press an arrow key right after clicking a rotate
button once, and try `Space` too** — `Space` is unmapped, so it is the one key a focused button
could plausibly steal.

Also worth a look, both consequences of correct behaviour rather than bugs:

- **The rotate buttons move.** They are right-aligned to the photo, and the photo's width depends
  on the rotations of all three visible photos (the equal-height rule sizes to the widest). So the
  buttons shift horizontally *and* vertically as you rotate. It is consistent, but it cost me
  three attempts to automate and may feel unsettled in the hand.
- **Rotating one photo resizes its neighbours**, for the same reason.
