## Task A — the close-button hang

### Confirmed before fixing, exactly as the theory predicted

Reproduced first: after clicking the X, the window vanished but the process was **still alive
14 seconds later**. Dump taken of that live process, then analysed.

UI thread (STA, OSID `0x94f8`):

```
System.Threading.Monitor.Wait
System.Threading.ManualResetEventSlim.Wait
System.Threading.Tasks.Task.SpinThenBlockingWait
System.Threading.Tasks.Task.InternalWaitCore
System.Runtime.CompilerServices.TaskAwaiter.HandleNonSuccessAndDebuggerNotification
Fastcull.MainWindow.MainWindow_Closed(...)   [MainWindow.xaml.cs @ 44]
WinRT ... TypedEventHandler ... Do_Abi_Invoke
Microsoft.UI.Xaml.Application.Start
Fastcull.Program.Main
```

`dumpasync`, one stack only:

```
<< Awaiting: System.Runtime.CompilerServices.ValueTaskAwaiter >>
  Fastcull.ViewModels.MainViewModel+<ShutdownAsync>d__11
    System.Threading.Tasks.Task+SetOnInvokeMres
```

Line 44 was `ShutdownAsync().GetAwaiter().GetResult()`. `SetOnInvokeMres` is the
`ManualResetEventSlim` that `GetResult()` creates in order to block. So the UI thread was
blocked waiting on a continuation that itself needed the UI thread. **Textbook sync-over-async
deadlock — theory confirmed, not assumed.**

### One tooling note worth keeping

**ProcDump's `-h` hang detector never fired.** Windows still reported the process as
`Responding: True`, because by the time `Closed` runs the window is already destroyed — there is
no unresponsive *window* to detect, only a process that never exits. The dump had to be taken by
PID (`procdump -ma <pid>`). Worth remembering: `-h` is the wrong tool for a
never-exits-after-close bug.

### The fix — both layers, as instructed

1. `ShutdownAsync` now uses `ConfigureAwait(false)`, so it can never require the UI thread to
   resume and cannot deadlock a blocking caller.
2. `Window.Closed` is replaced by cancelable `AppWindow.Closing`. First close is cancelled, the
   flush runs as ordinary awaited async work with the dispatcher still pumping, then `Close()`
   is called again. A flag stops the second pass re-entering the cancel branch, and it is set in
   a `finally` so **a failed flush cannot trap the user in a window that refuses to close**.

### Verified

- **5 of 5 close cycles exited cleanly** — checked that the *process* was gone via
  `Get-Process`, not merely that the window disappeared. The pre-fix build was still alive after
  15 s.
- **A rating made ~100 ms before clicking X survives.** Drove a real `SetStars(5)` through the
  `AppCommand` path, clicked X 100 ms later, then read the session database directly: 100 rows
  registered, `_MG_4175.jpg → Picked, stars=5`. The H.2 guarantee still holds.
- **ProcDump is not left running**, and `-i` was never used — only `-w` and by-PID, neither of
  which registers anything machine-wide, so no `-u` cleanup is needed.

## Task B — RAW Tier A/B, measured across the whole corpus

### Method

Surveyed **every RAW file** in the current `SampleImages/` (96 RAW of 100 files total: 76 `.ARW`,
20 `.CR2`, 4 `.jpg`). For each: EXIF full-image width via `MetadataExtractor`, and the largest
**decodable** embedded JPEG stream. Files were scanned **end to end**, not through the
production 16 MB window, specifically so that window could be validated too.

### Result — the finding holds, and it is unanimous

| Format | Files | Preview ≥ 90% of full width (PRD 5.1 `FullResIsCheap`) |
| :--- | :--- | :--- |
| `.ARW` | 76 | **76 / 76 — 100%** |
| `.CR2` | 20 | **20 / 20 — 100%** |
| **Total** | **96** | **96 / 96 — 100%** |

- No file had only a small (~1616×1080-class) preview.
- No file lacked a decodable preview.
- **0 of 96** had their largest preview beyond the 16 MB production scan window — that window is
  validated by measurement, not guesswork.

The embedded preview is not merely *near* full width; in both families it is **exactly the full
image dimensions**:

- `.ARW` — `Exif Image Width` 7008 → preview **7008×4672** (100%)
- `.CR2` — `Exif IFD0 Image Width` 6000 → preview **6000×4000** (100%)

One measurement nuance, stated so the numbers can be trusted: my survey took the *maximum* of
all EXIF width tags as the denominator. For `.CR2` that is 6288 (`[Exif Image] Image Width`, the
masked sensor width including border pixels), not the 6000 actual image width, which is why the
raw table shows 95% for CR2. **6288 is the conservative denominator; against the real full-image
width the figure is 100%.** Either way it clears the 90% threshold comfortably.

### Reporting, not deciding — as instructed

**The finding from last run was not a small-sample artifact.** It holds at 96/96.

On the face of it this means RAW zoom would be **Tier A**, and the GPU-debayer contingency in
PRD 3.4 may be unnecessary. **I have not touched PRD 1.7 or 3.4** — that is your call. Two
caveats to weigh before you make it:

- This is **two camera bodies**. A body that embeds only a small preview would still land in
  Tier B, and PRD 1.7's 1616×1080 figure did come from a real `exiftool` check, so it plausibly
  describes some `.ARW` variant or camera setting not present here (compressed vs. lossless RAW,
  or a different quality setting, would be the first things I would check).
- Tier A also requires the preview to be *usable* at 1:1, not merely present. This survey
  measured dimensions only. It did not assess preview JPEG quality, and a heavily compressed
  full-size preview may not be acceptable for critical-focus checking, which is what zoom is
  for.

### Code: not committed, deliberately

The survey was a throwaway console outside the repo. **I did not commit it.** It duplicates the
JPEG-stream scanner that already lives in `RawPreviewDecoder`, and a second copy would rot out of
sync with the real one. The method is described above precisely enough to re-run, and the
production scanner is already covered by the test suite.
