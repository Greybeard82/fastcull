## Task A — the gap really was the columns

Your diagnosis was right, and confirmed against the code before changing it. Two changes:

1. **`Auto` columns, grid centred.** A slot now takes exactly its photo's width, so the only
   horizontal space between photos is the spacing.
2. **The sizing rule**, replacing equal-thirds-divided-by-the-widest with

   `min(availableHeight, (availableWidth − totalGapWidth) / sumOfVisibleAspects)`

The two rules agree *exactly* whenever the visible photos share an aspect — there is a test
asserting that against the old arithmetic — so the common all-landscape case regressed nothing.

**Measured on a portrait/landscape/landscape set:** gaps of **4px and 5px** (the 4 is sub-pixel
rounding at a photo edge), identical whether the neighbour is portrait or landscape, which is
A.4's acceptance criterion. The three photos plus gaps sum to exactly the 1408px available.
Landscape photos went from ~465px wide to **572px**.

One structural consequence: `StageHost` now owns the available space, because the stage sizes to
its own content and centres — its width is the photos' width, not the room they have.

## Task B — landed, and here is what it does

**Not abandoned.** The escape hatch was there for a good reason and I read B.4 before starting,
but the restructure went in cleanly, so this is the "working variable stage" outcome rather than
the "working three-slot stage" fallback.

### What made it tractable

The thing B.4 warned about — the repeater fighting `ApplySlot`'s explicit sizing — was avoided by
not doing it that way. Instead of resolving realized containers and assigning sizes to them, all
the geometry moved onto the item as **bound properties** (`StageFrameWidth`, `StageImageLeft`,
`StageTickWidth`, …), computed once per layout pass by `ApplyStageMetrics(sharedHeight)`. The
template binds them; nothing is looked up by name.

That sidesteps the `ItemsRepeater` DataContext problem entirely rather than working around it —
and where an index genuinely is needed, `Slot_Tapped` uses `GetElementIndex`, exactly as
`Thumbnail_Tapped` already did.

### The rule, and the cap

The stage expands outward while the set is still **height**-bound — while the shared height is
clamped by the available height and the set therefore does not yet span the width. Once width
binds, the set already fills the stage and one more photo would only shrink all of them.

- **Counts stay odd** (1, 3, 5, 7, 9) so "the active photo is the centre slot" is literally true.
  An even count has no centre, and PRD 1.5's positioning rule is preserved exactly: centred
  except at the boundaries, where the window cannot extend past the end.
- **Cap: 9.** As B.2 required, stated here explicitly. **This raises the ceiling on simultaneous
  display-tier decodes from 3 to 9** — see the PRD 3.3 note at the end.

### Measured

| Set | Slots | Result |
| :--- | :--- | :--- |
| All portrait | **5** | 5 photos at 271px each, **every gap exactly 5px**, spanning 1375 of 1408 available |
| Portrait + 2 landscape | 3 | Correct — width binds immediately, so growing would only shrink |
| 3 portrait with a landscape neighbour | 3 | Correct — expanding to 5 would pull in a landscape photo and shorten all of them |

That last row is the rule earning its keep: it declines to show more photos when doing so would
make every photo smaller.

## Task D — animation

### The bug first

`CenterOn` was called from `Thumbnail_Tapped` and nowhere else, exactly as D.1 says. Centring now
runs from `OnNavigated`, which fires for every navigation source. Verified by navigating with
**stage clicks** — a source that never touched the strip before — and watching the strip follow.

### What I chose

- **Duration: 110 ms**, cubic ease-out, as `NavigationSlideMilliseconds` in
  `Themes/Nocturne.xaml`.
- **Stage:** a `TranslateTransform` on a container that paints no background (PRD 1.10). Starts at
  the outgoing offset, settles at zero.
- **Bottom strip:** `ChangeView`'s own eased scroll, **not** a composition animation. I evaluated
  it as D.2 asked and it already reads as the intended slide — measured, the strip moves through
  83 → 81 → 78 → 76 → 74 → 73 → 71 rather than jumping. A composition animation would have been
  fighting the `ScrollViewer` for ownership of the offset for no gain, and `ChangeView` already
  retargets rather than queues when called again mid-scroll.

### The slide, measured

Capturing a single scanline as fast as possible (a full-window grab with per-pixel reads was far
too slow to catch 110 ms — the first attempt saw only the start and end positions):

```
t= 50ms  290      t= 88ms   67      t=116ms   21
t= 55ms  243      t= 94ms   52      t=122ms   18
t= 61ms  201      t=100ms   41      t=128ms   17
t= 67ms  165      t=105ms   32      t=133ms   16  (settled)
t= 72ms  134      t=111ms   25
t= 78ms  107
t= 83ms   85
```

Sixteen intermediate positions, step sizes shrinking 47 → 42 → 36 → 31 → … → 1. Visible, and
fast.

### Interruptible and coalescing

Each navigation reads the offset the content is **currently drawn at**, adds the new shift, and
animates that to zero — so it converges on the settled position instead of accumulating a
backlog. The offset is clamped to two slot pitches so a long hold cannot wind up an absurd
distance to unwind.

**Tested with 20 rapid navigations** fired 40 ms apart: settled cleanly, final state coherent,
nothing wedged. **This is not the same as holding a key** — see below.

Drag is not fought: centring bails while `_dragging`.

## Changed without being asked

1. **`ComputeCellWidth` → `ComputeTotalGapWidth`.** The old helper computed an equal share, which
   the new rule does not use. Rather than leave it as dead code I replaced it with the thing the
   new rule *does* need, keeping the tested one-fewer-gaps-than-slots off-by-one guard.
2. **`ComputeSetWidth`** added, so "does the set fit?" is asked in one tested place.
3. **Two converters replaced.** `ActiveSlotToTickBrush`/`ActiveSlotToCaptionBrush` keyed off
   `MainViewModel.ActiveSlot` with a hardcoded slot index as `ConverterParameter`; with a variable
   count there is no fixed index to pass, so both now take the item's own `IsActive` bool.
4. **`Thumbnail_Tapped` no longer calls `CenterOn`** — `OnNavigated` does it for every source, so
   the explicit call was redundant.
5. **Task C's functional changes are inside the Task B commit**, not their own. Task B rewrote the
   exact markup Task C targets; splitting them would have meant authoring the old three-slot
   caption structure purely to replace it one commit later. `b566bd9` carries the comment
   corrections and records the C measurements.

## PRD 3.3 — more urgent than before

**`docs/tasks/2026-08-23-followup4.md` (the prefetch window and LRU cache) is still unrun, and
this task made it more pressing, not less.**

Task B **raised the ceiling on simultaneously-staged photos from 3 to 9**, and every staged photo
holds a display-tier decode that nothing evicts. The 5.25 GB peak-working-set failure measured in
the followup3 benchmark was against a three-slot stage; the worst case is now three times wider.
The cap of 9 exists precisely to bound that, but a bound is not a fix.

**Re-read followup4 against the current code before executing it.** What changed underneath it:

- The stage is a variable-length `StageItems` collection, not three fixed slot properties.
- Per-item stage geometry now lives on `FilmstripItemViewModel` and is recomputed per layout pass.
- Any eviction logic must not discard rotation — that is user data, not a decode artefact.
- `OnNavigated` is now the single place navigation side-effects hang off, which is the natural
  place for prefetch to hook in.
