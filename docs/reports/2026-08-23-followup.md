## Task C — the suspected cause was wrong

The work order predicted a missing `[NotifyPropertyChangedFor]`. **Those attributes were
already there**, added during the overnight run. The ViewModel had been notifying correctly all
along. The bug was in the XAML.

The three top slots bound the badge's `Visibility` to the item **reference** through a converter:

```xml
Visibility="{x:Bind ViewModel.Slot0Item, Mode=OneWay,
             Converter={StaticResource StarBadgeVisible}}"
```

A binding on the reference only re-evaluates when a *different item* enters that slot — never
when the item already sitting there raises `PropertyChanged`. Meanwhile `StarBadgeText` and
`StateBorderBrush` used nested paths (`ViewModel.Slot0Item.StarBadgeText`), which x:Bind *does*
subscribe to.

That asymmetry is exactly the symptom you reported: **the border tracked the ladder, the badge
did not**, and it only caught up on deselect/reselect because that swapped the item in the slot.
The bottom thumbnails were never affected — inside the `DataTemplate` they bind the item's own
properties directly.

Fix: bind the top slots through nested paths instead. Null-safety is unchanged, because every
such element sits inside the `Grid` governed by `ItemToVisibilityConverter`, so an empty slot
still renders nothing.

**The same latent bug existed on the decode-failure placeholder** (`DisplayFailed`, also bound
to the item reference): a decode that failed while the photo was already on screen would never
have shown its warning glyph. Fixed the same way — which mattered immediately, since Task D
introduces a decode path that can fail per-file.

## Task D — RAW works, with no new package

### LibRawSharp is unusable (tried first, as instructed)

- Only version on nuget.org is **0.0.2**, ~2,100 total downloads.
- Ships **`lib/netstandard2.0/LibRawSharp.dll` and nothing else** — no native binaries in any
  runtimes folder. Calling `LibRaw.RawImage.Load` throws
  `DllNotFoundException: Unable to load DLL 'LibRawNative.dll'`.
- Its entire public API is `Load` / `Width` / `Height` / `Data`. **It exposes no thumbnail or
  preview extraction** — no `unpack_thumb`. Even working, it would only have offered a full
  debayer, which D.2 explicitly wanted to avoid.

Magick.NET was therefore never needed and **was not evaluated** — the approach below made it
unnecessary well inside the time budget.

### What actually works: the embedded JPEG preview

Measured against the real corpus:

| File | Embedded JPEG streams found |
| :--- | :--- |
| `DSC02769.ARW` | 160×120 thumb, **1616×1080** preview, **7008×4672 full-size** |
| `_MG_0460.CR2` | 160×120 thumb, **6000×4000 full-size** |

Every tier this app needs is already present as ordinary JPEG. `RawPreviewDecoder` finds those
streams by scanning the first 16 MB for JPEG SOI/EOI markers — deliberately vendor-agnostic,
since Sony and Canon place previews at different offsets under different maker-note tags — then
hands the bytes to the same WIC scaled-decode the JPEG path already uses.

Candidates are tried **smallest-first**, so the thumbnail tier decodes the 160×120 thumb rather
than the full-size preview, and the 24 MB lossless-JPEG *sensor data* inside a `.CR2` is only
reached last, where it fails to decode (`Unsupported JPEG data precision 14`) and is skipped.

**Measured: ~30 ms to extract and decode, versus ~1000–1200 ms for WIC's full debayer of the
same file**, against PRD 3.5's 250 ms budget.

### A finding that contradicts PRD 1.7 — worth your attention

PRD 1.7 states the A7C II embedded preview is ~1616×1080, and concludes from that RAW zoom will
be **Tier B** (needing a debayer), calling the debayer number "the most important number in this
document".

**That preview exists, but the `.ARW` files also embed a full 7008×4672 JPEG** — full sensor
width. If that holds across your corpus, **RAW zoom is Tier A, not Tier B**, and the GPU-debayer
contingency in PRD 3.4 may never be needed. I have not changed PRD 1.7 — that is your call, and
I have only sampled a handful of files.

### WIC's role

WIC *does* decode `.ARW`/`.CR2` on this machine, so the Store **Raw Image Extension is installed
here**. It is wired in only as a per-file fallback when preview extraction returns null. Saying
this plainly, as D.3 asked: **this is not a substitute for a primary decoder** — it would fail on
a clean machine, which is precisely why PRD 1.1 wants LibRaw primary. Today the primary path is
preview extraction, which depends on nothing external.

Anything still null falls through to the existing error placeholder — per PRD 1.1, a file that
fails to decode is never silently dropped.

**The `b8c6eec` crash fix was not touched.** As D.4 required, I checked the disposal hazard:
`RawPreviewDecoder` returns the same `SoftwareBitmap` type, so the existing rule in
`ApplyDecodeResultAsync` — never dispose once `SetBitmapAsync` has taken ownership — already
covers it.
