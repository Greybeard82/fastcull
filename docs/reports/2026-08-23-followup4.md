## 0. The blocking precondition

The work order says not to start until the visual/UX redesign is finished, committed,
and has its own report. **It is.** Commit `7d6b7c1` plus
`docs/reports/2026-08-23-followup6.md` (the redesign ran across followup5 and
followup6). I re-read every file before touching it rather than trusting followup3's
description, which the work order specifically warned about — and that mattered:
`FilmstripItemViewModel` had been substantially restructured, and the stage is no
longer three fixed slots.

Two things changed since the work order was written, both of which the eviction design
had to account for and neither of which the original 3-slot scoping anticipated:

1. **The stage shows a variable 3–9 photos** (followup6's aspect-ratio layout). At nine
   it spans ±4, which is **wider than the window's own −2 lookbehind**. A keep-set of
   "the window" alone would therefore cancel loads the stage had just started, on every
   navigation. The keep-set is the window **UNION** the pinned stage set, and that union
   is the reason the code reads the way it does.
2. **A zoom tier exists** (~30 MB of BGRA8). Only one is alive at a time and it is
   released on zoom-exit or photo-change, so it does not accumulate — but it is real
   peak pressure, so it is measured mid-session rather than on an empty heap, and it is
   counted in `ResidentBytes` from a **measured** size rather than an estimate, because
   guessing it would make the ceiling meaningless whenever zoom is open.

## 1. Task-by-task

### Task A — decode follows the cursor, not the constructor ✅

`FilmstripItemViewModel`'s constructor started both a thumbnail and a display decode
unconditionally, and `MainViewModel.LoadAsync` constructed one per scanned file in a
tight loop. That is the mechanism behind 4,000 concurrent decode jobs at 2,000 files.
Confirmed still true post-redesign before changing it.

The constructor now decodes **nothing**. Two independent load axes, each with its own
`CancellationTokenSource` and started flag:

| Axis | Driven by | Why separate |
| :--- | :--- | :--- |
| `BeginLoad` / `CancelLoad` | the prefetch window | display tier, ~2.4 MB |
| `BeginThumbnailLoad` / `CancelThumbnailLoad` | `ItemsRepeater` realizing a container | the strip shows every photo in the folder, so gating thumbnails behind the window would leave most of it blank |

New: `Fastcull.Core/Services/DecodeGate.cs` (bounded pool) and
`Fastcull.Core/ViewModels/ICacheableItem.cs`. **The seam exists for a hard reason**: the
WinUI project cannot be referenced from a test project (its MSIX targets refuse to build
ProcessorArchitecture-neutral), so without `ICacheableItem` none of this logic would be
verifiable at all.

### Task B — sliding window and bounded worker pool ✅

`PrefetchWindow`: +5 ahead, −2 behind, reversal after three consecutive moves.
`DecodeGate`: `SemaphoreSlim(min(6, coreCount − 2))` — 6 workers on this 12-core machine.

**One deliberate deviation from the spec, flagged as the work order asks.** PRD 3.3
specifies reversal after three consecutive *backwards* moves and says nothing about
reverting. Reverting on a single forward step would make the window thrash on any
jitter — a user who steps back three and forward one is still going backwards. Reversal
is therefore **symmetric**: three consecutive moves in *either* direction set the
orientation. This is a deliberate reading of the rule rather than a literal one.

### Task C — LRU eviction, 3 GB ceiling ✅

`PrefetchCoordinator`. Three rules in order of authority: pinned wins, in-window loads,
everything else is fair game. Eviction sorts furthest-from-cursor first.

**Nothing is disposed.** I read the `0xC000027B` comment block first, as instructed.
Eviction drops the ViewModel's own managed references and lets WinRT refcounting and the
GC reclaim. `Evict()` also returns early when pinned, so a currently-staged photo can
never be selected as a victim — blanking a photo the user is looking at is a visible bug,
not a memory saving.

### Task D — 512 MB dimension guard ✅

`Fastcull.Core/Services/DimensionGuard.cs`. Caps any decode to 512 MB of BGRA8
(134 MP) by solving `longEdge = sqrt(maxPixels × longOverShort)` for the source's aspect.
Applied at the two places a decode size is actually chosen: inside
`DecodeScaledFromStreamAsync` (where the source dimensions are known) and at the top of
`LoadZoomImageAsync` (where the viewport drives the request).

`DimensionLimited` raises an on-photo **"1:1 UNAVAILABLE — IMAGE TOO LARGE"** badge, so a
capped photo reads as capped rather than as a mysteriously soft decode. PRD 3.3 asks for
"a HUD notice"; there is no HUD in v0.1 (CLAUDE.md forbids it), so this is the simplest
equivalent in the current UI, matching the existing `ThumbnailFailed` / `DisplayImageFailed`
pattern.

The oversized-image test builds a 6000×4000 PNG at test time rather than committing a
large binary fixture.

### Task E — re-measurement ✅ — and a defect it caught

Full numbers in `docs/benchmarks/2026-08-23-post-prd33.md`. See §2 below.

**The measurement found a real bug in my own Task C code.** The first run reported
**266,035 evictions across 2,000 navigation steps** — 133 per step. That is thrashing, not
eviction, and the cause was genuine:

> `Evict()` deliberately keeps the bottom filmstrip's thumbnail. But `EvictToCeiling`
> credited itself the victim's whole `ResidentBytes`. A photo the cursor has already
> passed therefore holds a thumbnail and nothing else, frees **nothing** when evicted —
> and the sweep still counted 68 KB reclaimed. Those items sort furthest-from-cursor, so
> they absorbed the entire pass, and **the display tiers that should have been dropped
> were never reached.**

Fixed in commit `659e01e`: `ICacheableItem` gained `EvictableBytes` so the sweep can tell
what an item *holds* from what evicting it would *give back*; the loop now measures
`ResidentBytes` before and after and credits only the difference; and the candidate list
is allocated and sorted only when the total is actually over the ceiling, since this runs
on every keypress. Result: **266,035 → 745 evictions.**

**Why the unit tests missed it, which is the part worth remembering.** `FakeItem.Evict()`
freed everything — a behaviour the real view-model never has. The fake now models both
tiers separately, and three tests cover the thumbnail-survives-eviction case directly.
A green suite was not evidence the evictor worked; a 2,000-file measurement was.

## 2. The numbers

Same methodology as the 5.25 GB baseline in `docs/benchmarks/2026-08-23-baseline.md`:
same harness, same 2,000-file synthetic hard-linked corpus, same `Process.WorkingSet64`
sampling at 25 ms, Release build, same machine. The legacy eager-fan-out row is
**deliberately still measured** so the before/after is a like-for-like comparison in a
single run rather than a comparison across two runs on different days.

### Peak working set, 2,000 files — budget < 4 GB

| Architecture | Peak | Status |
| :--- | ---: | :--- |
| Eager fan-out (baseline, 2026-08-23) | 5.25 GB | **FAIL** |
| Eager fan-out (re-measured this run) | 5.16 GB | **FAIL** |
| **PRD 3.3 window + LRU eviction (ships now)** | **3.26 GB** | **PASS** |
| With a 30 MB zoom held mid-session | 2.60 GB | PASS |

The two eager-fan-out numbers agreeing to within 2% is the control: it confirms the
5.25 GB → 3.26 GB improvement is the architecture, not a difference between the two runs.

**A 38% reduction, and — more importantly — it is now bounded rather than linear.**

### Next/previous, cache hit — budget < 16 ms — previously NOT MEASURABLE

| Measurement | Median | p95 | Status |
| :--- | ---: | ---: | :--- |
| While the decode pipeline is saturated | 11.3 ms | 14.5 ms | PASS |
| **The decision alone, heap quiesced** | **10.1 µs** | 10 µs | PASS |

Reported as two rows because one would have been actively misleading. 11.3 ms sitting
just under a 16 ms budget reads as "the cache barely makes it." It is not: the decision
itself — stage window, pin pass, and the coordinator's O(n) sweep over all 2,000 items —
costs **10 microseconds**, three orders of magnitude inside budget. The 11.3 ms is what
GC pauses from concurrent decoding cost the navigating thread when the pipeline is
running flat out. That is a real cost the app pays and it is honest to show it, but it is
not a reason to change the coordinator, and conflating the two would have pointed at the
wrong fix.

Hit rate was **100% (1,999 hits, 0 misses)**. A step that had to decode is recorded as a
miss and excluded from the timing, so this row cannot silently report a decode as a
cache hit.

### Everything else — no regressions

Full scan 217 ms (< 8 s) · first image 231 ms (< 1.5 s) · cache-miss display tier
22.6 ms RAW / 8.1 ms JPEG (< 250 ms) · rating keypress 0.1 µs (< 16 ms). All still pass.

### The crossover: ~1,400–1,500 → the failure mode is gone, not moved

followup3 derived ~1,400–1,500 photos from a **linear** model: 2.5 MB per item, nothing
ever released, so memory grows without bound until it crosses 4 GB.

**That model no longer applies.** Resident memory is now capped by the 3 GB ceiling
regardless of folder size. Measured: 2,000 photos held 3,074 MB of tracked pixels against
a 3,072 MB ceiling — it fills and then stays filled. Peak working set is therefore roughly
"ceiling + ~300 MB process overhead" for **any** folder above about 1,300 photos, which is
what the flat 3.26 GB is.

The one term still linear in folder size is the thumbnail cache: ~68 KB each, never
released (the strip may still be showing them), and counted *inside* the ceiling. So the
ceiling is only breached by thumbnails alone at roughly **3 GB ÷ 68 KB ≈ 45,000 photos** —
a ~30× improvement, and past the point where other things break first.

**Stated honestly: 45,000 is arithmetic, not a measurement.** I measured 2,000. The claim
I am confident in is the measured one — peak is flat at 3.26 GB and no longer grows with
folder size — not the extrapolated figure.

### Things in the PRD that proved wrong or underspecified

1. **The 3 GB ceiling and the 4 GB budget are in tension, and they were set
   independently.** The ceiling consumes 75% of the peak-working-set budget, and the
   measured peak lands at 3.26 GB — **16% headroom**. It passes, but it passes because the
   ceiling happens to fit, not with margin. A 2 GB ceiling would give real room and, given
   the window is only ~17 items, would cost nothing observable. Worth a decision.
2. **"LRU cache … evicting furthest-from-cursor first"** names two different policies.
   Distance-from-cursor is implemented, per the PRD's own qualifier — but it is not LRU,
   and the text reads as though they are the same thing.
3. **"a HUD notice that 1:1 is unavailable"** — there is no HUD in v0.1 and CLAUDE.md
   forbids building one. Implemented as an on-photo badge.
4. **PRD 5.2 names one file, `Services/PreviewCache.cs`**, for "prefetch window, LRU,
   RAM + VRAM ceilings, dimension guard, cancellation." Implemented as five, split by what
   needs WinUI and what does not: `Services/DecodeGate.cs`, `Services/DimensionGuard.cs`,
   `ViewModels/PrefetchWindow.cs`, `ViewModels/PrefetchCoordinator.cs`,
   `ViewModels/ICacheableItem.cs`. The split is what makes the logic testable at all; the
   architecture tree should be updated to match reality.
5. **PRD 1.5 line 95 is now stale.** It reads "the peak-working-set budget in §3.5 already
   fails (see §3.3)" as a justification for the 9-slot cap. The cap is still right, but the
   premise is no longer true. I left it alone rather than edit it, because rewriting it is
   adjacent to declaring the budget passed, which is your call.
6. **PRD 6 schedules the dimension guard in v0.2, not v0.1.** The work order put it in
   this task, so it is built now. Same for zoom, which you asked for earlier this session.
   The PRD's phase boundaries and what is actually built have drifted apart in both
   directions and could use one reconciling pass.

### VRAM texture cache — deliberately not built

PRD 3.3's VRAM cache is explicitly v0.4 (PRD 6) and the work order forbids it here. Not
started. Note that every memory figure in this report is **system RAM only** — a
`SoftwareBitmapSource` also copies pixels into a XAML composition surface that may live in
GPU memory and is not this process's working set to sample.

## 4. Open questions

1. **The harness now always exits 1.** The legacy eager-fan-out row is kept deliberately
   as the before/after control, and it still FAILs its 4 GB budget — correctly, since it
   measures the architecture that was replaced. But PRD 3.5 wants this harness to become a
   build gate, and a permanently-failing row would permanently fail the build. Options:
   mark that row informational (`no PRD budget`), or have the gate ignore rows tagged
   historical. **I did not change it**, because turning a FAIL into a non-failure is
   exactly the kind of adjustment the work order told me not to make on my own judgement.
2. **Is 3 GB the ceiling you want?** See §3.1. This is the one number I would revisit.
3. **The corpus grew to 101 files** (77 `.ARW`, 20 `.CR2`, 4 `.jpg`) versus the baseline's
   100, so the two runs are not over a byte-identical corpus. It is a 1% difference and
   cannot move a GB-scale number, but the comparison is not exact and the results file now
   reads the count from the run rather than hardcoding it.
4. **GC pressure, not the cache, is what costs 11 ms under saturation.** If navigation ever
   feels sticky while the prefetch is working hard, that is the thing to attack — most
   likely by pooling or by Server GC — not the coordinator.

## 5. Things changed that were not asked for

- **`ICacheableItem.EvictableBytes`** — new interface member. Required to fix the eviction
  defect in §1 Task E; the sweep cannot otherwise distinguish a no-op eviction.
- **`MarkdownReport`** no longer hardcodes the title or the corpus size. The baseline file
  said "the real corpus is 100 files" in prose while the run measured 101 — a file whose
  whole purpose is to be trusted about its own methodology should not go stale silently.
  A `--title` flag was added so the baseline file can still be regenerated under its own
  name.
- **`ThumbnailService` tier constants** went `internal` → `public`, so the eviction
  estimate can derive sizes from the real tier values instead of duplicating them.
