## Task B — the perf harness

`Fastcull.Benchmarks`, a plain console app over `Fastcull.Core`. No WinUI, no dispatcher, no
window. Run it with:

```
dotnet run -c Release --project Fastcull.Benchmarks
```

It writes `docs/benchmarks/2026-08-23-baseline.md` and exits non-zero if a **measured** budget
fails. NOT MEASURABLE never fails the run — that's a gap in the app, not a regression in it.

I kept `Stopwatch` and added no packages. Nothing during the build changed my mind about
BenchmarkDotNet: PRD 3.5 wants a gate that runs routinely against absolute budgets, and every
number that matters here is tens of milliseconds or larger, well clear of the noise floor a
single-run harness leaves. The tradeoff is stated in the results file rather than hidden.

### What is deliberately not measured

Four PRD 3.5 rows have no number. None was approximated by timing something adjacent:

| Metric | Why |
| :--- | :--- |
| Next/previous, **cache hit** (< 16 ms) | PRD 3.3's prefetch window and LRU cache do not exist in any form. No cache means no cache-hit path to time. Timing a re-decode of a still-resident bitmap would measure something the app never does. |
| Enter zoom, Tier A (< 50 ms) | Zoom is v0.2. Nothing to enter. |
| Enter zoom, Tier B (< 400 ms) | Zoom is v0.2, *and* there is no debayer for the Tier B path to use (PRD 3.4's gap). |
| Pan at 1:1 (60 fps) | Zoom is v0.2, and frame rate needs a compositor and a real window. |

**This matters for the v0.1 gate.** PRD 6 ships v0.1 on "the perf harness and the first three
budgets from 3.5 enforced". Budgets one and two pass. **Budget three is the cache-hit row, which
cannot be enforced because the feature it measures was never built.** v0.1's own gate is
therefore not fully satisfiable today, regardless of the memory failure below.

### Honest caveats on the numbers above

- **The 2,000-file corpus is 2,000 NTFS hard links over the 100 real sample files — not 2,000
  real photos.** At an average 56 MB/file a real copy is ~112 GB, which I was not willing to
  write to your disk on every benchmark run. Hard links are genuine directory entries over real
  bytes, so enumeration, `FileInfo.Length` and header parsing all do real work. But 2,000
  entries share 100 extents, so the page cache is much warmer than reality.
- **Every timing is warm-cache.** The harness scans once to build fixture sets before timing
  anything. A genuinely cold first-open of a 2,000-file card off NVMe is *not* measured and will
  be slower. Read the scan and first-image rows as a floor.
- To bound that bias the harness also times the real 100-file corpus: **0.12 ms/file real vs.
  0.11 ms/file synthetic**. The linking is not distorting per-file scan cost meaningfully — but
  both are warm, so this bounds the *linking* bias, not the *cold-cache* one.
- **"First image" is a proxy**, as B.4 specified: folder-open to first decoded thumbnail. Pixels
  in hand, not pixels lit. It stops before the XAML marshal (~30 ms, previously measured).
- **The rating row is decision latency only** — `InputRouter.Resolve` + the `CullState`
  transition. See *Changed without being asked* for why the `PropertyChanged` half is missing.

## The B.5 finding: it is retention, not concurrency

You asked me to test the unbounded fan-out directly and report either way. **The fan-out itself
is fine. The retention is not.** I measured both, because conflating them would have produced
the wrong conclusion:

| Variant | Peak working set |
| :--- | ---: |
| Decode 4,000 jobs unthrottled, dispose each bitmap as it lands | **0.90 GB** — PASS |
| Decode 4,000 jobs unthrottled, **retain every bitmap** (what the app does) | **5.25 GB** — FAIL |

Reproduced twice: 5.26 GB and 5.25 GB.

**Why the fan-out survives.** `FilmstripItemViewModel`'s constructor does start both decodes for
every item with no throttle, and `RawPreviewDecoder` does allocate its 16 MB scan-window buffer
synchronously before its first await — so 4,000 jobs really do claim 16 MB each on the way in.
But the launch loop is itself slow enough (35 s for 2,000 files) that the GC reclaims completed
buffers faster than the loop creates new ones. Managed heap peaked at 680 MB. **Your B.5
hypothesis was reasonable and it did not bite.**

**Why retention doesn't.** `FilmstripItemViewModel` holds `Thumbnail` and `DisplayImage` for
every item it ever constructed, and deliberately does not dispose the `SoftwareBitmap` — its
lifetime passes to the `SoftwareBitmapSource` (that's the fix for the 0xC000027B crash, and it
is correct). Nothing ever evicts them, because the thing that would is PRD 3.3's LRU cache,
which does not exist. So at 2,000 files the app holds **4,000 decoded bitmaps simultaneously**,
forever.

At roughly **2.5 MB per item** (a ~160 px thumbnail plus a ~960 px display frame, both BGRA8),
the crossover is around **1,400–1,500 files** — that is where a real folder starts exceeding the
4 GB budget. A 2,000-image card is an entirely ordinary day's shoot, so this is reachable in
normal use, not a synthetic-only artifact.

I did **not** implement PRD 3.3, per the ground rules.

### What PRD 3.3 would need to be, scoped out

For you to decide whether this is the next task. PRD 3.3 already specifies most of it; this is
what it means concretely against the code as it stands:

1. **Move the decode out of the constructor.** This is the load-bearing change and the smallest
   one. `FilmstripItemViewModel` currently self-starts both tiers on construction. Decoding must
   instead be driven by the cursor, so only items inside the window ever decode at all.
2. **Sliding window** — active index +5 / −2 on a bounded pool of `min(6, coreCount - 2)`, with
   the direction-aware reversal after three consecutive backwards moves. PRD 3.3 as written.
3. **Eviction, which is the part that actually fixes the 5.25 GB.** LRU keyed by distance from
   cursor, hard RAM ceiling. Evicting means dropping the `ImageSource` reference and letting the
   `SoftwareBitmapSource` go — and given the 0xC000027B history, eviction must not dispose a
   `SoftwareBitmap` that a composition surface may still be copying from. That is the one genuinely
   delicate part of this work and deserves its own test.
4. **Dimension guard** — the 512 MB decoded ceiling. Independent of the above and cheap; it
   currently does not exist either, so one stitched panorama is still an OOM.
5. **Not in scope for closing this budget:** the VRAM texture cache. PRD 6 puts it in v0.4, and
   the measured failure is system RAM, not VRAM.

Rough sizing: items 1–3 are the real work and interact with the cursor logic in `MainViewModel`;
item 4 is nearly standalone. It is a genuine feature, not a patch — which is why it is on your
desk rather than in this commit.

**One thing worth knowing before scoping it:** with a window of even 100 resident items, peak
would land near 250 MB. There is enormous headroom. The fix does not need to be clever, it needs
to exist.
