## Task C — Window-level keyboard routing

### C.1 The problem

Arrow keys do not reach the app's handler. `FilmstripView` currently handles
`KeyDown` on the `UserControl` itself, which fails once focus moves into the
bottom `ScrollViewer` / `ItemsRepeater` — those consume arrow keys for
scrolling and XY-focus navigation before the handler ever sees them.

PRD 2.3 already mandates the fix: *"Input routing is an explicit two-state
machine, handled in one place at window level."*

### C.2 Implement

Create `Input/InputRouter.cs` — a **pure, XAML-free, static class**. This is the
part that gets tested, so it must not reference any WinUI type other than
`Windows.System.VirtualKey`.

```csharp
public enum AppCommand
{
    None,
    NavigatePrevious,
    NavigateNext,
    NavigateFirst,
    NavigateLast,
    LadderUp,
    LadderDown,
    SetStars,        // payload 0-5
    SetPicked,
    SetRejected,
    SetUnflagged,
}

public readonly record struct ResolvedInput(AppCommand Command, int Payload);

public static class InputRouter
{
    public static ResolvedInput Resolve(VirtualKey key, bool isExtendedKey);
}
```

### C.3 The NumLock rule — this is the part that is easy to get wrong

PRD 1.6 flags this as an explicit v0.1 test case that "fails silently".

With NumLock **off**, the numpad emits navigation keycodes: `NumPad2` arrives
as `Down`, `NumPad4` as `Left`, and so on — colliding with real navigation.

**Discriminate using the extended-key flag.** In Windows, the genuine grey
navigation keys set the extended-key bit; their numpad equivalents do not.
In WinUI this is `KeyRoutedEventArgs.KeyStatus.IsExtendedKey`.

Resolve as follows:

**`isExtendedKey == true` — genuine navigation keys:**

| Key | Command |
| :--- | :--- |
| `Left` | `NavigatePrevious` |
| `Right` | `NavigateNext` |
| `Up` | `LadderUp` |
| `Down` | `LadderDown` |
| `Home` | `NavigateFirst` |
| `End` | `NavigateLast` |

**`isExtendedKey == false` — numpad with NumLock off:**

| Key | Command |
| :--- | :--- |
| `End` | `SetStars(1)` |
| `Down` | `SetStars(2)` |
| `PageDown` | `SetStars(3)` |
| `Left` | `SetStars(4)` |
| `Clear` | `SetStars(5)` |
| `Insert` | `SetStars(0)` |
| `Right`, `Home`, `PageUp`, `Up` | `None` (numpad 6/7/9/8 are unmapped) |

**Always, regardless of the extended flag:**

| Key | Command |
| :--- | :--- |
| `Number1`–`Number5`, `NumberPad1`–`NumberPad5` | `SetStars(1..5)` |
| `Number0`, `NumberPad0` | `SetStars(0)` |
| `P` | `SetPicked` |
| `X` | `SetRejected` |
| `U` | `SetUnflagged` |
| anything else | `None` |

### C.4 Wire it up

- Handle keys **once**, at the window root, using **`PreviewKeyDown`** on
  `MainWindow`'s root element. `PreviewKeyDown` tunnels from the root downward,
  so you intercept before the `ScrollViewer` ever sees the key.
- For every key that resolves to something other than `AppCommand.None`, set
  `e.Handled = true`. This is what stops the bottom strip scrolling.
- Belt and braces on the bottom region: set `IsTabStop="False"` on the
  `ScrollViewer` and the `ItemsRepeater`, and
  `XYFocusKeyboardNavigation="Disabled"` on the `ScrollViewer`.
- Log unmapped keys at debug level rather than swallowing them silently
  (PRD 2.2 requires this).
- **Do not** implement key-repeat coalescing. PRD section 6 schedules that for
  v0.4. Just make sure holding a key does not crash or corrupt state.

both extended and non-extended, including the collision cases. This is the
