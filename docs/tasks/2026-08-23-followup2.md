## Task A — The close-button hang

### A.1 What's already found — confirm it, don't re-derive it

`MainWindow.xaml.cs`, `MainWindow_Closed`:

```csharp
private void MainWindow_Closed(object sender, WindowEventArgs args)
{
    try
    {
        Filmstrip.ViewModel.ShutdownAsync().GetAwaiter().GetResult();
    }
    ...
```

`ViewModels/MainViewModel.cs`, `ShutdownAsync`:

```csharp
public async Task ShutdownAsync()
{
    if (_sessionStore is null) return;
    var store = _sessionStore;
    _sessionStore = null;
    await store.DisposeAsync();   // <-- no ConfigureAwait(false)
}
```

`SessionStore.DisposeAsync()` itself is clean — every internal `await` already uses
`ConfigureAwait(false)`. But the `await store.DisposeAsync();` line above does not, so it
captures the UI thread's `SynchronizationContext` to resume on. Meanwhile
`MainWindow_Closed` blocks that same UI thread synchronously via `.GetAwaiter().GetResult()`.
The continuation has nowhere to run. This is a textbook sync-over-async deadlock —
suspected root cause of "closes via X does nothing, needs Task Manager to kill."

### A.2 Confirm it with a hang dump before fixing

Same tooling as the crash investigation, already installed (`procdump`,
`dotnet-dump`). This time use ProcDump's **hang** detector instead of its exception
detector:

```
procdump -accepteula -ma -h -w Fastcull.exe C:\dumps
```

`-h` writes a dump when the process has an unresponsive window for 5+ seconds. Launch
the app, click the X, wait for the hang, let ProcDump capture it.

```
dotnet-dump analyze "<dump path>" -c "clrthreads" -c "clrstack -all" -c "dumpasync" -c "exit"
```

Confirm: the UI thread (the STA one) is parked inside `MainWindow_Closed` /
`GetAwaiter().GetResult()`, and there is a completed-or-completing `DisposeAsync`
task with a continuation that never ran. If the dump shows something else entirely —
say, the writer task itself is still blocked on SQLite, not a marshaling issue — report
that instead and fix the real cause. Don't force this theory onto different evidence.

### A.3 Fix

Once confirmed, there are two layers to this, do both:

1. **Immediate fix:** `await store.DisposeAsync().ConfigureAwait(false);` in
   `ShutdownAsync()`. This alone should resolve the specific deadlock found.
2. **Structural fix, because blocking a UI thread synchronously inside `Window.Closed`
   is fragile even once this one path is patched** (by the time `Closed` fires, the
   window's message pump may already be tearing down, which makes any synchronous
   wait here a bad pattern regardless of `ConfigureAwait`). Replace the `Closed`-based
   approach with `AppWindow.Closing` (cancelable):
   - On first `Closing`, set `args.Cancel = true`.
   - Kick off `Filmstrip.ViewModel.ShutdownAsync()` as a normal awaited async
     operation (no blocking call).
   - When it completes, call `Close()` again (a flag prevents re-entering the cancel
     branch a second time) so the window actually closes once the flush is done.
   - This way the flush runs with the UI thread's dispatcher still pumping normally,
     which is the state async code is supposed to run in.
