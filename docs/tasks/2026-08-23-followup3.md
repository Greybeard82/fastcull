## Task A — PRD 1.7 / 3.4: update to Tier A

### A.1 What changes and why

The 96-file survey in the last run (76 `.ARW`, 20 `.CR2`, both camera bodies) found
**100%** of files carry an embedded preview at full sensor width, not the small
~1616×1080 preview PRD 1.7 assumed from its original single-camera `exiftool` check.
David has decided: update the PRD now, on this evidence.

### A.2 Rewrite PRD 1.7's conclusion

Keep the section's structure (Tier A/Tier B definitions, the zoom mechanics) but
replace the concluding assessment. It currently says the A7C II's preview is
undersized and "every RAW zoom will need a full debayer decode (Tier B), this is the
normal case." Replace with something like:

> A 96-file survey across two camera bodies (Sony `.ARW`, Canon `.CR2`) found 100% of
> RAW files carry an embedded JPEG preview at full sensor width — `.ARW` at
> 7008×4672, `.CR2` at 6000×4000, both matching their sensor's real image width
> (not a masked/bordered EXIF tag). This means RAW zoom is **Tier A for both formats
> tested**: no debayer decode is needed, the embedded preview is usable directly.
>
> This is not a guarantee for every camera or RAW variant. Two caveats: only two
> bodies are represented in the survey, and a full-size preview's *dimensions*
> matching the sensor does not by itself confirm its JPEG compression quality
> survives 1:1 critical-focus inspection — that can only be confirmed once zoom mode
> (v0.2) is actually built and tested against it. `FullResIsCheap` in PRD 5.1 already
> encodes the fallback: any RAW file whose preview is below the 90% threshold still
> routes to Tier B automatically.

### A.3 Update PRD 3.4

The GPU-debayer line currently reads RAW debayer as "Substantial" GPU benefit with
"CPU now, GPU later" as the decision, and commits `CpuDebayer (LibRaw)` to ship in
v0.2 with `GpuDebayer` as a v0.5 drop-in "if measurement shows RAW zoom lands in
Tier B."

Update to reflect both the Tier A finding **and** the fact that LibRaw died as a
dependency (found in the RAW decoding task: LibRawSharp ships no native binary and
has no preview-extraction API). Be honest about the resulting gap rather than paper
over it — something like:

> Per PRD 1.7's updated finding, RAW zoom is Tier A for every file surveyed so far,
> which means debayer performance is no longer the critical path it was assumed to
> be. The GPU-debayer contingency for v0.5 is deprioritized on this basis.
>
> **Open gap, not silently resolved:** no working debayer implementation currently
> exists in this codebase. `LibRawSharp` (the package this PRD originally named) was
> evaluated and found unusable — no native binary ships with it, and it exposes no
> preview-extraction API either. If a future RAW file is ever encountered whose
> embedded preview genuinely falls below the `FullResIsCheap` threshold, it will
> currently have **no full-resolution decode path at all** and would need to degrade
> to the upscaled-preview-with-decoding-indicator behavior PRD 1.7 describes for Tier
> B, indefinitely, since there is nothing to decode with. `IRawDebayer` remains an
> unimplemented interface. If this gap needs closing, `Magick.NET-Q16-HDRI-x64` is
> the next candidate to spike, not LibRaw.

### A.4 Update PRD 5.2 dependencies

The line `LibRawSharp or Magick.NET-Q16-HDRI-x64 (RAW only, spike before building on
it)` should reflect what's actually true now: neither is a dependency of the shipped
code (RAW decoding uses only WIC, via embedded-preview extraction, PRD 3.2). Reword
to note LibRawSharp was spiked and rejected (reason above), Magick.NET was never
evaluated because it wasn't needed, and either remains a future candidate only if
Task A.3's gap ever needs closing.

### A.5 Update PRD section 7's risk table

## Task B — The v0.1 perf harness (PRD 3.5)

### B.1 What "done" means here

PRD section 6 gates v0.1 on "the perf harness and the first three budgets from 3.5
enforced": first image on screen < 1.5s, full scan (2,000 files) < 8s, next/previous
cache hit < 16ms. Build the harness now, but read B.4 before assuming all three can
be honestly asserted — one of them can't, for a real reason, not a shortcut.

### B.2 Structure

Add `Fastcull.Benchmarks`, a plain console project referencing `Fastcull.Core`
directly (not the WinUI `Fastcull` project — most of what needs measuring is already
WinUI-free, and keeping the harness free of WinUI/dispatcher dependencies makes it
fast, deterministic, and runnable from the command line without a window ever
opening, which matches PRD 3.5's implicit expectation of a CI-style regression gate,
not a UI-timing tool). Add it to `Fastcull.sln`.

### B.3 Fixture sets

PRD 3.5: "Benchmarks run against three fixture sets: all-RAW, all-JPEG, and mixed.
The mixed set is the one that finds bugs." Derive these as filtered views over
`SampleImages/` (now ~150 files) by `FormatFamily` — don't hand-curate a separate
folder.

**For the two budgets defined at "2,000 files"** (full scan, and peak working set —
see B.5), the real corpus won't reach that count. Generate a synthetic corpus to
reach ~2,000 files by copying existing sample files under new names into a
**gitignored** scratch directory (e.g. `Fastcull.Benchmarks/synthetic-corpus/`, added
to `.gitignore`) — never commit synthetic fixture data. State the real vs. synthetic
file counts clearly in the report; don't let a reader assume 2,000 real photos were
used.

### B.4 What can and cannot be honestly measured today — read before writing assertions

- **"First image on screen from folder selection" (< 1.5s):** measure end-to-end
  from `DirectoryScanner.ScanAsync` start to the *first* item's thumbnail-tier
  decode completing (via `ThumbnailService`/`RawPreviewDecoder`, both already in
  `Fastcull.Core`, no dispatcher needed). This is a close proxy for the real metric —
  it stops short of the final XAML `SoftwareBitmapSource` marshal, which prior
  measurement already showed costs roughly 30ms, negligible against a 1.5s budget.
  Say plainly in the report that this is what was measured, not literal pixels on
  screen.
- **"Full scan, 2,000 files" (< 8s):** directly measurable, `DirectoryScanner`
  timing against the synthetic corpus from B.3.
- **"Next/previous, cache hit" (< 16ms): CANNOT be honestly asserted.** PRD 3.3's
  prefetch window and LRU cache were never built in any session so far — there is no
  cache, so there is no "hit" code path to measure. Do not fake this by, say, timing
  a second decode of an already-in-memory bitmap and calling it a cache hit; that is
  not what the app does today. State clearly that this specific budget row requires
  PRD 3.3 to exist first, and it doesn't.
- **"Next/previous, cache miss" (< 250ms): CAN be honestly asserted — and should be,
  it's a bonus, not required by PRD 6's "first three."** Since there is no cache yet,
  every navigation *is* a cache miss today. Measure per-item decode latency
  (thumbnail and display tier, across RAW and JPEG) as exactly this.
- **"Rating keypress to border change" (< 16ms): also worth asserting, also a
  bonus.** Measure `CullState.Up()`/`.Down()`/etc. plus the resulting
  `PropertyChanged` firing on `FilmstripItemViewModel` — purely in `Fastcull.Core`
  and its ViewModels, no XAML compositor involved. Say plainly that this measures
  the app's own latency up to raising the property-changed notification, not the
  GPU-scheduled compositor repaint that follows it, which is outside the app's
  control to benchmark meaningfully.
- **"Enter zoom" (both tiers) and "Pan at 1:1": cannot be measured at all.** Zoom
  doesn't exist yet (v0.2). Don't stub anything to produce a number — state they're
  blocked on a feature that isn't built.

### B.5 Peak working set — and the concurrency question to actually test

Measure `Process.GetCurrentProcess().WorkingSet64` (or `GC.GetTotalMemory` alongside
it, report both) while loading the synthetic ~2,000-file corpus through the same
decode path a real folder-open uses.

**Read this before running it.** `FilmstripItemViewModel`'s constructor currently
starts *both* decode jobs (thumbnail and display tier) for **every** item the moment
it's constructed, with no windowing — `MainViewModel.LoadAsync` constructs one
`FilmstripItemViewModel` per scanned file in a loop with nothing throttling how many
run concurrently. At 150 sample files this is invisible. At 2,000 it may not be: this
could mean roughly 4,000 concurrent decode jobs firing at once, no cap.

Test this directly and report what actually happens — CPU/thread-pool behavior,
peak memory, and whether the "first image on screen" budget from B.4 is still met
*at 2,000-file scale specifically*, not just on the small real corpus. If the
eager-decode-everything behavior blows the memory budget or measurably delays the
first image, **that is the finding** — say so plainly, name the missing piece (PRD
3.3's sliding-window prefetch, never built), and stop. **Do not implement PRD 3.3 to
fix it.** That's a real, separately-scoped feature (sliding window, direction-aware
reversal, LRU eviction, VRAM budget) — report it as the likely next task, don't fold
it into "building a benchmark."

### B.6 Why not BenchmarkDotNet

PRD 3.5 wants a regression gate ("a regression greater than 25% fails the build"),
which wants something fast and deterministic enough to run routinely, not a
statistically-rigorous micro-benchmark suite with warm-up iterations that takes
minutes per run. A `Stopwatch`-based harness that runs the real pipeline once or a
handful of times and asserts against the PRD's absolute budgets fits PRD 5's
architecture diagram (a single `Benchmarks/PerfHarness.cs`, not a dedicated
benchmarking framework) and this project's no-new-packages default better. If you
disagree after starting this, say why in the report rather than silently adding a
package.

### B.7 Output

Two things:
- The harness itself, runnable via `dotnet run --project Fastcull.Benchmarks`
  (or as `dotnet test`-visible cases if that fits better — your call, say which).
- A results file, `docs/benchmarks/2026-08-23-baseline.md` (or `.json`, your call):
  every measured metric, its value, the PRD budget it's checked against, pass/fail,
  and — critically — the metrics from B.4 that are explicitly **not measurable
  yet**, with the reason, so this file reads as a complete and honest picture, not a
  partial one dressed up as complete. This becomes the reference point for the "25%
  regression fails the build" rule PRD 3.5 wants; wiring that into an actual CI gate
  is future work, not this task.
