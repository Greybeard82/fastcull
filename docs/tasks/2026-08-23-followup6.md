## Task A — The gap is not the gap

### A.1 Root cause

`Views/FilmstripView.xaml`, the stage `Grid`:

```xml
<Grid x:Name="Stage" ColumnDefinitions="1*,1*,1*"
      ColumnSpacing="{StaticResource StageColumnSpacing}">
```

Each column is a fixed **one third of the stage width**, and each slot's `StackPanel`
is `HorizontalAlignment="Center"` inside it. A landscape photo nearly fills its third,
so the 5px `ColumnSpacing` reads as the whole gap. **A portrait photo is only
`0.667 × sharedHeight` wide inside a cell a third of the screen wide**, so the visible
space between photos becomes cell-width-minus-photo-width — hundreds of pixels — and
`ColumnSpacing` is irrelevant to it. That is the black canyon in the screenshot. The
5px setting is doing exactly what it says; the columns are the problem.

### A.2 Fix the columns

Columns must size to their content, and the row of them must centre as a whole:

- `ColumnDefinitions="Auto,Auto,Auto"` on the stage `Grid`, with the `Grid` itself
  `HorizontalAlignment="Center"`.
- `ApplySlot` already sets an explicit frame width per slot, so `Auto` columns will
  take exactly the photo's width. The only horizontal space left between photos is
  then the real `ColumnSpacing`.

### A.3 Fix the shared-height rule — this is the part that buys real estate

`Fastcull.Core/ViewModels/StageLayout.cs` currently computes:

```
sharedHeight = min(cellHeight, cellWidth / widestVisibleAspect)
```

and `UpdateStageLayout` feeds it `cellWidth = (stageWidth - spacing*2) / 3`.

That rule assumes every photo gets an equal third whether it needs it or not. Replace
it with one that fits the actual set into the actual width:

```
sharedHeight = min(availableHeight, (availableWidth - totalGapWidth) / sumOfVisibleAspects)
```

Why this is the right rule, not just a different one:

- **Identical output when all photos share an aspect.** Three 3:2 photos: old gives
  `((W-gaps)/3)/1.5 = (W-gaps)/4.5`; new gives `(W-gaps)/4.5`. Nothing regresses for
  the common case.
- **Strictly larger photos whenever aspects differ.** One portrait beside two
  landscapes: the old rule sizes everything to the widest and leaves the portrait's
  unused third as dead space. The new rule spends that space on height for all three.
- It makes the gap literally the gap, which is what A.2 needs to be true.

Keep the existing guarantees: never crop, fall back to `DefaultAspectRatio` for an
undecoded or non-finite aspect, return 0 when there is no room. Height must still be
clamped by the available height so a set of narrow photos does not grow past the stage.

`UpdateStageLayout` must stop dividing by 3 and pass the full available width plus the
total gap width instead.

### A.4 Verify

- `Fastcull.Tests/StageLayoutTests.cs` has 10 tests against the old signature. Update
  them, and **add cases the old rule got away with**: mixed portrait/landscape sets,
  an all-portrait set, and a set where the height clamp binds rather than the width.
  The sample corpus is all landscape, so these cases only exist in tests — and now
  also at runtime via rotation, which is how this bug reached the screen at all.
- In the running app: rotate one photo to portrait and confirm the space between it
  and its neighbours is the same 5px as between two landscape photos.

Commit.

## Task B — Render as many photos as actually fit

David: *"visibility is top priority, and if more photos fit on either side of the
carousel, feel free to render them."* This is authorized, and it is the largest change
in this task file. **Read B.4 before starting.**

### B.1 Why it follows from Task A

After Task A, three portrait photos are height-bound, not width-bound: they sit
centred with a lot of unused width either side. That slack is exactly what extra
photos should fill. The count should follow from the geometry, not be fixed at three.

### B.2 The rule

Expand outward from the active photo while the set still fits:

- Start from the active index. Add neighbours alternately (ahead, behind, ahead…),
  stopping when adding one more would make
  `sum(sharedHeight × aspect_i) + gaps > availableWidth` at the height the set would
  then require, or when the sequence runs out at either end.
- **Preserve PRD 1.5's positioning rule:** the active photo sits centred in the set,
  except at the sequence boundaries — at the first photo the window cannot extend
  behind it, at the last it cannot extend ahead. The window still never scrolls past
  either end.
- **Cap the count.** Pick a hard maximum (9 is a reasonable ceiling) and state it in
  the report. Uncapped, a folder of extreme-portrait crops on an ultrawide could
  realize a dozen-plus simultaneous display-tier decodes — and the known 5.25 GB
  retention failure from the followup3 benchmark is not fixed yet, because PRD 3.3 has
  not been built. Do not make that worse without a ceiling.

### B.3 What this touches

`MainViewModel` exposes `Slot0Item`, `Slot1Item`, `Slot2Item` and `ActiveSlot` as
three hardcoded properties, and `FilmstripView.xaml` has three hand-written slot
blocks with `x:Name`d elements (`Slot0Frame`, `Slot0Image`, `Slot0Rotate`, `Slot0Tick`,
`Slot0Bar`, and their 1/2 twins) that `ApplySlot` is called against by name. A variable
count means replacing all of that with a collection plus a templated repeater, and
resolving elements per realized container rather than by name.

`Fastcull.Tests/FilmstripWindowTests.cs` tests the three-slot window and will need to
follow.

### B.4 The escape hatch — use it rather than half-finishing

This is a genuine restructure, not a tweak. If partway in it becomes clear it cannot
be done cleanly in this pass — the templated-repeater layout fights `ApplySlot`'s
explicit sizing, or `x:Bind` in the template can't reach what it needs (note the
project has already hit `ItemsRepeater` not propagating `DataContext` under `x:Bind`,
which `Thumbnail_Tapped` works around via `GetElementIndex`) — then **stop, revert
this task's changes, report what blocked it, and carry on to Task C against the
existing three-slot structure.** A working three-slot stage with correct 5px gaps is a
good outcome; a half-migrated stage is not. Say clearly in the report which of the two
happened.

Commit (or report the abandonment).

## Task C — Active-slot chrome: alignment, and following the selection

Apply this to whatever structure exists after Task B.

### C.1 The middle photo sits higher than its neighbours

**Root cause:** every slot's `StackPanel` is `VerticalAlignment="Center"`. The centre
slot's caption row contains the two rotate `Button`s, which are taller than the 10px
caption text in the other two. The centre slot is therefore taller overall, and
centring it vertically pushes its photo **up** by half the excess. That is the "raised
the top limit ever so slightly" in the screenshot.

There is a second, related defect: `CellChromeHeight` is built from
`CaptionHeight = 14`, described as "10px type, measured line box". If the button row is
taller than 14px, the shared-height computation is also working from a stale number and
every photo is slightly taller than it should be.

**Fix:** give the caption row **one fixed height, identical in every slot**, sized to
comfortably contain the buttons, and constrain the buttons to sit within it rather than
grow it. Update `CaptionHeight` (and therefore `CellChromeHeight`) to that value so the
layout math and the markup agree.

**Verify by measurement, not by eye:** with the buttons visible, the top edges of all
photos must be at an identical Y. A screenshot comparison of the top edges is the
acceptance test — this is a ~3px defect and "looks fine now" is not evidence.

### C.2 The rotate buttons must follow the selected photo

Currently the buttons are hardcoded inside slot 1's markup with a comment saying they
"sit under the centre slot always, but act on the ACTIVE item". That was my
instruction in the previous task and **it was wrong** — David wants them under the
photo they act on, which at the first and last photo of the sequence is an end slot,
not the centre.

Change it: the buttons render in the **active** slot, wherever that is, and nowhere
else. Exactly one slot shows them at a time. They continue to act on the active item
(that part is already correct — keep it).

The accent tick above the active photo is already keyed on `ActiveSlot` via
`TickBrush` + `ConverterParameter`. **Verify it is actually correct at both sequence
boundaries** rather than assuming it: navigate to the very first and very last photo
and confirm the tick and the buttons are both on the same slot as the highlighted
caption and the lit weight bar.

### C.3 Do not regress keyboard routing

`RotateButtons_Tapped` and the button styling exist partly to stop focus moving into a
child control and swallowing keys — this project has already lost arrow-key handling
that way once. After moving the buttons, **explicitly re-test that arrows, `Z`/`X`/`C`,
`A`/`S` and the number keys all still work after clicking a rotate button**, at a
boundary slot as well as the centre.

## Task D — Navigation animation, both carousels

David: *"a slide animation when moving from one photo to another, very fast but still
visible."*

### D.1 First, a bug: the bottom strip does not move on keyboard navigation at all

`CenterOn(index)` is called from **`Thumbnail_Tapped` only**. Keyboard navigation never
calls it, so arrowing through a folder leaves the bottom filmstrip wherever it was and
the active thumbnail simply drifts off screen. Fix this as part of this task — the
strip must keep the active thumbnail in view on every navigation, whatever the source.

### D.2 The animation

- **Duration:** fast but perceptible. Target **90–140 ms** with an ease-out curve;
  pick a value, put it in `Themes/Nocturne.xaml` as a named duration so it is tunable
  in one place, and say what you chose in the report.
- **Top stage:** when the window shifts, the photos should read as sliding by one slot
  pitch rather than snapping. Animate a horizontal translation on the stage content
  that starts at the outgoing offset and settles at zero.
- **Bottom strip:** animate the scroll to the new centred offset. Note `CenterOn`
  already passes `disableAnimation: false` to `ChangeView`, so some easing may already
  be available there — evaluate whether that reads as the intended slide or whether it
  needs a composition animation to be visible, and say which you used and why.

### D.3 Non-negotiable constraints

- **The state change is immediate; the animation is decorative.** Rating, selection and
  the active index must update on the keypress, never on animation completion. Nothing
  may wait for a transition to finish.
- **Interruptible and coalescing.** Holding an arrow key must not queue animations or
  fall behind the input. A navigation arriving mid-animation retargets the in-flight
  animation rather than enqueuing another. Test by **holding** left and right for
  several seconds, not by tapping — a queueing bug only shows under key repeat.
- **Do not fight the drag handling.** The bottom strip's pointer-drag path sets
  `HorizontalOffset` directly and guards on `_dragging`; an animation must not run
  against a drag in progress or snap-back on release.
- **OLED:** any container introduced to host the transform must not paint a
  background. Check it against PRD 1.10.
