## Task C — Fix the star badge not updating live

### C.1 The bug, exactly as reported

Changing a photo's rating while it stays the active/selected photo does not update
the star badge immediately. The badge only catches up once the photo is deselected
(loses active state) and presumably re-selected or its container gets re-evaluated.
Per PRD 1.6 (and CLAUDE.md's non-negotiable perf budget in PRD 3.5): *"A rating
keypress updates the border within one frame."* The border evidently does update
(section 3 of the checklist passed on colour) — it is specifically the **star
badge** that lags.

### C.2 Likely cause — verify before fixing

`FilmstripItemViewModel` almost certainly has `CullState` as the single
`[ObservableProperty]`, with `StarBadgeText` / `IsStarBadgeVisible` /
`StateBorderBrush` as separate, derived, get-only properties computed from it.
CommunityToolkit.Mvvm's source generator only raises `PropertyChanged` for the
property you decorated — it does **not** know that three other properties are
derived from it unless you tell it to.

**Check the actual generated code and property declarations first.** If this
theory is right, the fix is one of:

- Add `[NotifyPropertyChangedFor(nameof(StarBadgeText))]`,
  `[NotifyPropertyChangedFor(nameof(IsStarBadgeVisible))]`,
  `[NotifyPropertyChangedFor(nameof(StateBorderBrush))]` (repeat as needed for
  every derived property) on the `[ObservableProperty] CullState` field, **or**
- Implement the generated partial hook `partial void OnCullStateChanged(CullState
  value)` and call `OnPropertyChanged(nameof(StarBadgeText))` etc. inside it.

Either is fine; pick whichever fits the existing code style. If the actual cause
turns out to be something else entirely (e.g. an `x:Bind` mode issue, a
virtualization/container-reuse quirk in `ItemsRepeater`), say so and fix that
instead — don't force this theory onto a different bug.

### C.3 Scope

Apply the fix everywhere the badge and border render: all three top slots and
every bottom-filmstrip thumbnail. Last night's fix for the crash and the ladder
touched both; make sure this one does too.

### C.4 Verify, don't assume

You cannot send real keystrokes in your sandbox (same limitation as last night).
Drive the fix the same way the overnight run verified the ladder: through the
`AppCommand` dispatch path directly, on a photo that stays active throughout, and
confirm the badge text changes on **every single step** of the ladder — not just
before/after a full run. Take screenshots at a few intermediate steps (e.g. after
setting 2 stars, then 4 stars, while never deselecting) as evidence, the same way
last night's report showed evidence rather than asserting success.

## Task D — RAW files (.CR2, .ARW) don't load

### D.1 Current state

Only the 5 JPEGs in `SampleImages/` render anything. The 30 `.ARW` and 22 `.CR2`
files show blank — expected and documented as such in last night's report, since
the RAW decode path was explicitly out of scope. It is in scope now.

`FilmstripItemViewModel`'s constructor currently only starts a decode when
`photo.Family is FormatFamily.Jpeg or FormatFamily.Png` — RAW is skipped entirely,
by design, with a comment explaining RAW stays blank until this task.

### D.2 Read this before choosing a decode strategy — it changes the shape of the task

PRD 1.7 and the original project handoff notes both establish, via a real
`exiftool` check against this exact camera's files, that the embedded RAW preview
in Sony A7C II `.ARW` files is approximately **1616×1080** against a 7008×4672 (or
7040×4688, sources vary slightly) sensor.

Compare that to this codebase's actual tiers, in `Services/ThumbnailService.cs`:
`ThumbnailLongEdge = 160`, `DisplayLongEdge = 960`.

**1616 px comfortably covers both.** That means for the two tiers this app
actually needs *tonight* (thumbnail and display — see PRD 3.2, "3. Full
resolution" is zoom-only and out of scope until v0.2), **you should not need a
full RAW debayer decode at all.** Extracting the embedded JPEG/preview image and
downscaling it the same way `ThumbnailService.DecodeScaledAsync` already
downscales a WIC-decoded bitmap should be sufficient, fast, and far lower-risk
than a full debayer pipeline.

This does not necessarily hold for `.CR2` (different camera, unverified preview
size) — check rather than assume. If `.CR2` previews turn out too small for the
display tier, that's fine: fall back to a full decode for that family only, and
say so.

**This is the spike PRD section 7 calls for. Budget it real time — call it 45
minutes — not the PRD's throwaway "ten minutes," but do not let it eat the whole
session either. If a chosen library doesn't build, doesn't expose preview
extraction, or fails on the actual sample files within that budget, move to the
next option below rather than fighting one library indefinitely.**

### D.3 Order of attempts

1. **LibRawSharp.** Check it installs and builds on .NET 9 / x64. Check whether it
   exposes embedded-thumbnail/preview extraction (LibRaw's native API calls this
   `unpack_thumb`) rather than forcing a full `unpack()` + debayer. Try it against
   one `.ARW` and one `.CR2` from `SampleImages/`.
2. **If LibRawSharp fails or is unmaintained:** try `Magick.NET-Q16-HDRI-x64`.
   ImageMagick's RAW support and whether this specific build includes embedded
   preview extraction is genuinely unverified — check rather than assume. It may
   only expose a full decode; if so, that still works, just slower, and the
   dimension guard from PRD 3.3 becomes more relevant.
3. **If both fail entirely:** check whether WIC (already used for everything else,
   via `ThumbnailService`) can decode `.ARW`/`.CR2` at all on this machine — it can
   only if the *Raw Image Extension* from the Microsoft Store is installed
   locally, which is not guaranteed on a clean machine (this is exactly why the
   PRD wants LibRaw as primary, not WIC, for RAW). If it happens to work here,
   that's useful for tonight's local testing but **is not a substitute** for a
   real primary decoder — say so plainly if you end up relying on it.
4. **If nothing works:** stop, document exactly what you tried and where each
   attempt failed, and leave RAW blank as it is now. This is an acceptable
   outcome — PRD section 7 anticipated it. A clear "this doesn't work and here is
   the evidence" is worth more than a fragile decode path nobody can trust.

### D.4 If you get a working decoder

- Create `Services/LibRawDecoder.cs` per the architecture in PRD section 5 (name
  it to match whatever library you actually used if `LibRawDecoder` would be
  misleading — e.g. `RawDecoder.cs` — and say which library and why in the
  report).
- Same contract as `WicDecoder`/`ThumbnailService`: async, takes a
  `CancellationToken`, runs entirely off the UI thread, returns thumbnail and
  display tier bitmaps.
- Prefer embedded-preview extraction per D.2. Only fall back to a full decode for
  a format/file where preview extraction isn't available or is too small for the
  display tier.
- Wire into the dispatch: extend `FilmstripItemViewModel`'s constructor condition
  to include `FormatFamily.Raw`, routing to the new decoder. If the RAW decoder
  throws or returns null for a specific file, fall back to attempting `WicDecoder`
  once (in case the Store extension is present), then to the error-placeholder
  state already defined for failed decodes (`ThumbnailFailed`/`DisplayImageFailed`)
  — per PRD 1.1, a file that fails to decode is never silently dropped.
- **Do not touch the crash fix from `b8c6eec`.** The same bitmap-disposal-timing
  rule applies to whatever new bitmap type a RAW decode produces — check whether
  it has the same "don't dispose while XAML's async surface copy still holds it"
  hazard before assuming it's safe to dispose eagerly.

### D.5 Tests

Add a smoke test (in `Fastcull.Core`/`Fastcull.Tests`, following the
`DirectoryScanner` smoke-test pattern already there) that decodes a handful of
real `.ARW` and `.CR2` files from `SampleImages/` and asserts: no exception,
non-null result, reasonable pixel dimensions (not 0×0, not absurdly larger than
the source). This cannot cover the actual on-screen render (same
keyboard/rendering sandbox limits as before) but it proves the decode path itself
works against real files, which is the part most likely to be silently broken.

### D.6 Verify visually

Launch the app, screenshot the filmstrip with RAW files visible, confirm they
render actual photo content (not blank, not an error placeholder) in both the top
slots and the bottom thumbnails. If some RAW files succeed and others don't (e.g.
ARW works, CR2 doesn't), say exactly which and why, with evidence — don't round up
to "RAW support added" if it's partial.

Commit — or, if D.3 concluded nothing works, commit whatever spike code is worth
keeping (or nothing) plus a findings note, and say so clearly in the final report.
