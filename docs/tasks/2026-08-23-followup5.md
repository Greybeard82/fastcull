## Task A — Tighten the stage spacing

### A.1 The trap: two values must change together

The gap is defined in **two** places and they must stay in sync:

- `Views/FilmstripView.xaml`, the stage `Grid`: `ColumnSpacing="34"`.
- `Views/FilmstripView.xaml.cs`: `private const double StageColumnSpacing = 34;`

That constant is not decorative — `UpdateStageLayout()` uses it to derive the cell
width the equal-height rule is computed from:

```csharp
var cellWidth = (stageWidth - (StageColumnSpacing * 2)) / 3;
```

**Change only the XAML and the photos will be sized against a cell width that no
longer exists**, leaving them smaller than their cells with mystery whitespace — the
exact opposite of what this task is for. Change both, and prefer wiring them to a
single source of truth (bind the XAML `ColumnSpacing` to the constant, or define it
once as a resource the code-behind reads) so this cannot drift again.

### A.2 The values

- Stage column spacing: **34 → 5**.
- Stage outer padding: the `Border Grid.Row="0" Padding="40,18,40,24"` becomes
  **`8,18,8,24`** — horizontal only. **Leave the vertical padding (18 top, 24 bottom)
  alone**; it is carrying the tick above and the weight bar/caption below, and
  squeezing it would crowd the state marks the Chromeless look depends on.
- Both should end up as named constants/resources, not magic numbers buried in
  markup, so David can dial them without hunting.

### A.3 Verify

- `UpdateStageLayout`'s arithmetic still produces sane numbers — the existing
  `StageLayout` tests cover the rule itself, but add or adjust a test if the cell-width
  derivation moves anywhere testable.
- Look at the running app. Photos should be visibly larger and nearly touching, with
  the tick, weight bar and caption still correctly sized to each photo's rendered
  width (`ApplySlot` derives the tick at 18% and the bar at 100% of photo width — both
  must still line up).

## Task B — Rotation: state, command, and keys

### B.1 The model

Rotation is a **per-photo quarter-turn count**, persisted. Represent it as a small
value — `0, 1, 2, 3` quarter-turns clockwise (or an enum; your call, but keep it an
integer in the database, not a string). `A` increments modulo 4, `S` decrements
modulo 4. Both wrap: rotating right four times returns to the original orientation.

**Define it as a delta on top of whatever orientation the decode produces**, not as
an absolute orientation of the final image. This matters — see Task E.

### B.2 Input layer

`Fastcull.Core/Input/InputRouter.cs`:

- Add `RotateRight` and `RotateLeft` to the `AppCommand` enum.
- Add `VirtualKey.A` → `RotateRight` and `VirtualKey.S` → `RotateLeft` to the **first**
  switch in `Resolve` (the one that resolves before the extended-key/numpad split,
  alongside `C`/`Z`/`X`). Both keys are currently unmapped — confirm that is still
  true rather than taking my word for it.
- Add tests in the same style as the existing `Z`/`X`/`C` coverage: both keys resolve
  correctly in **both** extended-key states (they are letter keys, so the NumLock
  split must not shadow them), and rotation commands never alter the cull state or
  move the cursor.

`ViewModels/MainViewModel.cs`: handle the two new commands in `Execute`, following the
shape `ApplyRating` already uses — **rotation applies to the active item only, is
synchronous, moves nothing, and changes no rating.**

### B.3 The rendering trap — read this before writing any XAML

`ApplySlot` in `Views/FilmstripView.xaml.cs` currently sets `image.Width` and
`image.Height` explicitly, derived from the shared height and the item's
`AspectRatio`, then sizes the tick and weight bar from that width.

Two things follow, and getting either wrong produces a broken stage:

1. **A 90°/270° rotation inverts the aspect ratio.** `FilmstripItemViewModel.AspectRatio`
   is currently set from the decoded bitmap as `PixelWidth / (double)PixelHeight`. The
   value fed into `StageLayout.ComputeSharedHeight` and `StageLayout.PhotoWidth` must
   be the **post-rotation** aspect, or the shared-height rule sizes against the wrong
   shape and the rotated photo overflows its cell or leaves a gap. The cleanest fix is
   for the ViewModel to expose an effective/rotated aspect that already accounts for
   rotation, so the View keeps consuming one property and the rule stays untouched.
   `StageLayout` itself should not need to change — it already handles mixed aspects
   correctly, it just needs to be told the truth.
2. **`RenderTransform` does not affect layout.** Slapping a `RotateTransform` on the
   `Image` will draw it rotated while it still *occupies* its unrotated box — so it
   will overlap its neighbours or get clipped, and the tick and weight bar will be
   sized to the wrong width. The layout box must be the **rotated** box. A workable
   shape: give the image a container sized to the post-rotation dimensions, and rotate
   the image about its centre (`RenderTransformOrigin="0.5,0.5"`) with the image's own
   width/height being the pre-rotation dimensions. Whatever approach you choose, the
   acceptance criterion is the same: **at 90°, the photo must sit fully inside its
   cell, uncropped, at the shared height, with the tick and weight bar matching its
   actual rendered width.**

**Do not re-decode to apply rotation.** Rotation is a display transform. Re-decoding
would waste the decode budget PRD 3.5 measures and would invalidate work the cache
(once PRD 3.3 lands) is meant to keep. Rotation must be effectively instant — treat
PRD 3.5's `< 16 ms` rating-keypress budget as the bar it has to clear.

### B.4 Thumbnails too

The bottom filmstrip thumbnails must show the same rotation as the stage — a photo
rotated on stage that stays sideways in the filmstrip is a bug, not a simplification.
Note the thumbnail row sizes items by a fixed width/height with its own mark bar; make
sure a rotated thumbnail still fits its slot without overlapping neighbours.

### B.5 The buttons

In the caption row beneath the **centre slot only** (slot 1), **right-aligned**: two
small buttons, rotate-left and rotate-right. Requirements:

- Visually consistent with the Chromeless look — this design language is built on
  restraint (9–11px wide-tracked chrome text, no borders, muted neutrals). Use the
  Nocturne tokens already in `Themes/Nocturne.xaml`; do not introduce new colours,
  and do not use a default WinUI `Button` chrome that will render a grey box in the
  middle of an OLED-black stage. Flat, borderless, transparent background,
  neutral glyph that brightens on hover.
- **PRD 1.10 is absolute: every non-photograph pixel must be exactly `#FF000000`.** A
  button background, hover fill, or focus visual that paints a near-black instead of
  true black violates it. Check the pressed/hover/focus visual states explicitly, not
  just the resting state.
- They act on the **selected** photo, which is the centre slot except at the sequence
  boundaries (PRD 1.5's three-slot rule — at the first photo the active slot is left,
  at the last it is right). **The buttons stay under the centre slot regardless**, but
  must always act on whatever is actually active. Do not wire them to "slot 1's item"
  — wire them to the active item, the same one `ApplyRating` uses.
- Clicking a button must not steal keyboard focus from the window-level
  `PreviewKeyDown` routing that drives everything else. This project has already been
  bitten once by focus moving into a child control and swallowing arrow keys — after
  wiring the buttons, **explicitly re-test that arrow keys, `Z`/`X`/`C` and the number
  keys all still work after clicking a rotate button.** If focus is a problem, set
  `IsTabStop="False"` and return focus to the root, but verify rather than assume.

## Task C — Persistence

### C.1 The migration trap — this will break existing databases if you miss it

`Fastcull.Core/Services/SessionStore.cs` creates its schema with:

```sql
CREATE TABLE IF NOT EXISTS photos ( ... )
```

`IF NOT EXISTS` is a **no-op against a database that already exists**. David has been
running this app, so real session databases already exist at
`%LOCALAPPDATA%\FastCull\sessions\{guid}.db` with the current column set. Adding a
`rotation` column to that `CREATE TABLE` statement will silently do nothing for those
databases, and the first rotation write will fail with `no such column: rotation`.

Handle this properly:

- Add a real migration step keyed on `PRAGMA user_version` (currently unset/0). On
  open, if the version is below the rotation revision, run
  `ALTER TABLE photos ADD COLUMN rotation INTEGER NOT NULL DEFAULT 0;` and bump
  `user_version`. Keep it idempotent and safe to run against both a fresh database and
  an existing one.
- Add the column to the `CREATE TABLE` statement as well, so new databases get it
  directly.
- **Test both paths**: a fresh database, and a database created *without* the column
  and then opened by the migrating code. The second test is the one that matters and
  is the one most likely to be skipped.

### C.2 Write and read paths

Rotation follows exactly the same route ratings already take — do not invent a second
mechanism:

- `QueueRating(string path, CullState state)` is the synchronous, non-blocking,
  `TryWrite`-based enqueue onto the batched channel writer (batch size 32, 250ms
  interval). Extend this path to carry rotation — either widen `RatingWrite` and the
  existing method, or add a sibling that shares the same channel and batching. Your
  call, but **the batching, the non-blocking guarantee, and the `ConfigureAwait(false)`
  discipline in the writer must be preserved.** There is an existing test asserting
  100 `QueueRating` calls do not block the caller; whatever you do must keep passing
  it, and rotation's path deserves the same assertion.
- `LoadRatingsAsync()` currently does `SELECT path, flag, stars FROM photos;` and
  returns a `Dictionary<string, CullState>`. It needs to return rotation too. Widen
  the return type to a small record/struct per photo rather than returning a second
  parallel dictionary — two dictionaries keyed by path that must be kept in sync is a
  bug waiting to happen.
- `MainViewModel.LoadAsync` must apply loaded rotation to each item on restore, the
  same way it applies loaded ratings today.

### C.3 Verify — this is the requirement David actually cares about

The acceptance test is behavioural, not unit-level: **rotate several photos, close the
app completely, reopen it on the same folder, and confirm every rotation is exactly as
left.** Do this for real, not only in tests. Include at least one photo rotated 180°
and one rotated 270° so a sign error or a modulo bug cannot hide.

Also confirm rotation survives the close path specifically — the app now flushes via
cancelable `AppWindow.Closing` (commit `dd946e0`), and a rotation made within ~100ms
of clicking the X must still land in the database. The existing rating-persistence
test covers this shape for ratings; mirror it.

## Task E — One thing to investigate and report, not fix

**There is no EXIF orientation handling anywhere in this codebase.** Grep confirms it:
no `Orientation` read, no transform applied at decode. The sample corpus is entirely
landscape 3:2, so this has never bitten.

The moment David culls a **portrait** shoot, every photo the camera tagged as rotated
will display sideways, and he will be manually rotating every single one with the
feature you just built — which is a worse outcome than not having the feature.

**Investigate and report; do not build it in this task.** Specifically:

- Confirm whether `MetadataExtractor` (already a dependency) exposes the orientation
  tag for the formats in play, and whether the embedded-JPEG preview extracted by
  `RawPreviewDecoder` carries its own orientation independent of the RAW container's.
- Confirm whether WIC's decode path applies orientation automatically for any format
  (it does for some, which would make behaviour *inconsistent between formats* — the
  worst case, and worth knowing).
- State what would need to change, and confirm that Task B.1's "rotation is a delta on
  top of the decode's orientation" framing means user rotations stored today stay
  correct if EXIF orientation is applied later. **If it does not — if adding EXIF
  handling later would silently re-interpret every stored rotation — say so loudly**,
  because that changes what should be stored now, and it is much cheaper to get right
  before David has rotated a few thousand photos than after.
