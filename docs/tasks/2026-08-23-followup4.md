## Task A — Move decode off the constructor, onto the cursor

### A.1 What's true as of the last measured state (confirm, don't assume)

`FilmstripItemViewModel`'s constructor started both the thumbnail and display-tier
decode unconditionally the moment the object was constructed, with nothing gating
it. `MainViewModel.LoadAsync` constructed one `FilmstripItemViewModel` per scanned
file in a loop, so opening a folder meant every single file started decoding at
once, immediately — this is what let 4,000 concurrent decode jobs happen at 2,000
files. Confirm this is still the shape of the code (post-redesign) before changing
it; if the redesign already restructured this, adapt the plan below to what you
actually find and say so in the report.

### A.2 The change

Decode must be driven externally, by window membership (Task B), not by
construction. Concretely: the ViewModel should expose something like
`Task LoadAsync(CancellationToken)` (or `BeginLoad`/`CancelLoad` — your call on the
exact shape, but it must be possible to start and cancel a load independently of
construction) rather than auto-starting in the constructor. Constructing a
`FilmstripItemViewModel` for every scanned file (which the app still needs to do, to
populate the filmstrip and its metadata) must no longer imply decoding it.

### A.3 Verify

A unit test (or set of tests) asserting that constructing N view-models does not, by
itself, trigger any decode calls — only an explicit load call does. Use the same
kind of fake/seam the existing tests already use for `ThumbnailService`/
`RawPreviewDecoder`, if one exists; if not, this is a reasonable place to add one.

## Task B — Sliding window and bounded worker pool

### B.1 What PRD 3.3 specifies

- Window: active index **+5 ahead, 2 behind**.
- Bounded worker pool: `min(6, coreCount - 2)`.
- Direction-aware: the window reverses after **three consecutive backwards moves**
  (i.e., if the user is paging backward repeatedly, stop assuming forward is "ahead"
  and swap which side gets the deeper lookahead).

### B.2 Implementation

This almost certainly lives in `MainViewModel` (or a new dedicated class it owns —
your call, but keep `MainViewModel` from becoming a god-object if this grows past a
screenful of logic; a `PrefetchWindow` or `CacheCoordinator` class in
`Fastcull.Core` is a reasonable split since it doesn't need WinUI). Responsibilities:

- On `SetActiveIndex` (or wherever the active index changes today — re-check the
  current name), compute the new window bounds.
- For items newly inside the window: call the `LoadAsync`/`BeginLoad` from Task A,
  respecting the worker-pool cap (a `SemaphoreSlim(min(6, coreCount - 2))` around the
  actual decode calls is enough — don't over-engineer a custom scheduler).
- For items that just left the window: cancel their in-flight load if one is running
  (the `CancellationToken` from A.2 exists for exactly this).
- Track the last 3 navigation directions to implement the reversal rule. A small
  ring buffer or even three bool fields is fine — this doesn't need to be clever.

### B.3 Verify

Unit tests against the windowing logic specifically — given a sequence of navigation
moves, assert which indices are inside the window at each step, and that a reversal
after three backward moves actually swaps the lookahead side. This should be testable
without touching real decode calls at all (fake/stub the load trigger).

## Task C — LRU eviction, 3 GB ceiling

### C.1 What PRD 3.3 specifies

LRU cache with a hard ceiling of 3 GB system memory, evicting furthest-from-cursor
first.

### C.2 Implementation — respect the crash history

**Read the comment block in `FilmstripItemViewModel` above the "NOTE: the
SoftwareBitmap is deliberately NOT disposed" line before writing any eviction code.**
That comment documents the exact native crash (`0xC000027B`,
`AsyncCopyToSurfaceTask::CopyOperation`) this project already hit once from disposing
a `SoftwareBitmap` while XAML's async composition-surface copy might still hold it.

Eviction must **never call `.Dispose()`** on a bitmap that has been handed to
`SoftwareBitmapSource.SetBitmapAsync`. Eviction means **dropping the ViewModel's own
managed references** (e.g. setting `Thumbnail`/`DisplayImage` back to null, or
whatever the current property names are) and letting normal WinRT reference counting
and the GC reclaim the underlying resources once nothing else holds them. If you find
yourself wanting to call `Dispose()` anywhere in this eviction path on an object that
has already been through `SetBitmapAsync`, stop — that is the exact bug this project
already paid to fix once.

One nuance worth naming explicitly in the report: an item currently bound to a
visible top-slot or filmstrip thumbnail still holds a reference from the XAML side
regardless of what the ViewModel's own cache does. LRU eviction is about the
**off-screen but still-resident** items — the ones the sliding window decoded ahead
of time but the user hasn't scrolled to yet. Evicting a currently-visible item's
image would be a visible bug (a photo going blank on screen), not a memory
optimization; make sure the eviction logic can't select a currently-bound item as a
candidate.

### C.3 Sizing

Track approximate memory per resident item (the followup3 report measured roughly
2.5 MB per item — a thumbnail plus a display-tier frame, both BGRA8 — that's a
reasonable estimate to seed this with, but measure via `GC.GetTotalMemory` /
`Process.WorkingSet64` deltas if you want a more precise number; don't over-invest in
exact byte accounting). When the tracked total crosses 3 GB, evict
furthest-from-cursor-first until back under the ceiling.

### C.4 Verify

- Unit test: given a synthetic sequence of loads exceeding the ceiling, assert the
  furthest-from-cursor items are the ones evicted, and that currently-windowed items
  are never evicted.
- This is the one part of this task that's worth a real, larger-scale check, not just
  unit tests: re-run (or extend) the `Fastcull.Benchmarks` retained-bitmaps peak
  working-set measurement from the last run, at the same 2,000-file synthetic corpus,
  with this eviction logic active, and confirm it actually comes in under 4 GB now.
  This is Task E below, but do a quick sanity pass here before moving on, since
  finding out only at the end that eviction doesn't actually reduce peak memory would
  waste the rest of this task's effort.

## Task D — Dimension guard (512 MB)

Independent of the cache work, cheap, and already scoped by PRD 3.3: any image whose
decoded size would exceed 512 MB in memory (roughly 128 MP at RGBA) should be capped
to a downscaled decode instead of decoding at full size, with a clear indicator (a
HUD notice per the PRD's language, or whatever the simplest equivalent is in the
current UI — a failed/limited-tier flag similar to the existing `ThumbnailFailed`/
`DisplayImageFailed` pattern is probably the natural fit) that full resolution isn't
available for that file. This does not currently exist; PRD 3.3 calls out a stitched
panorama TIFF as the concrete failure mode it prevents.

Verify with a test using a real or synthetic oversized image (a large synthetic PNG
generated at test time is fine — don't add a huge binary fixture to the repo).
