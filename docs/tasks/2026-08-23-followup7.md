## Task A — Restore the keymap

The working tree currently has `P`/`X`/`U` as the flag keys (with `X` meaning
Rejected), and `Up`/`Down` mapped to `SetPicked`/`SetRejected` with a comment noting
that nothing on the keyboard reaches the ladder any more. Both are wrong per the rules
above. Fix in `Fastcull.Core/Input/InputRouter.cs`:

- **`Z` → `SetRejected`, `X` → `SetUnflagged`, `C` → `SetPicked`.**
- **`P` and `U` are unmapped.** Not aliases — they do nothing, exactly as PRD 2.1
  already says. Assert this with explicit tests rather than by deleting the old ones.
- **`Up` → `LadderUp`, `Down` → `LadderDown`** (the extended-key path). The ladder must
  be walkable end to end: Rejected → Unrated → Picked → 1★ → 2★ → 3★ → 4★ → 5★, clamped
  at both ends. `CullState` already implements this correctly and is well tested — the
  bug is only that the keyboard stopped reaching it.
- **Keep `A` → `RotateLeft` (counter-clockwise) and `S` → `RotateRight` (clockwise).**
  The working tree's reversal is correct and matches the rule above. The stale comment
  in `MainViewModel` calling the *original* direction "deliberate and specified" should
  be corrected so it doesn't mislead the next reader.
- Keep `Space` → `ToggleZoom` and `Escape` → `ExitZoom`.

`Fastcull.Tests/InputRouterTests.cs` was rewritten for the P/X/U mapping. Restore its

## Task B — Zoom, at high resolution, including RAW

### B.1 What is already there, and what is missing

The working tree's zoom is further along than it first appears: `IsZoomed` on
`MainViewModel` mirrored onto items, `StageChromeVisibility` hiding the tick/bar/caption
while zoomed, `StageImageSource => ZoomImage ?? DisplayImage` so the softer image shows
from the first frame, `LoadZoomImageAsync(uint longEdge)`, a `_zoomCts` cancellation
path, and `ReleaseZoomImage()`. That structure is sound. Keep it.

**The gap is RAW.** The code comments say RAW is *excluded* from the zoom-tier decode
"on instruction" — a `.ARW` or `.CR2` keeps its display-tier image and never gets the
sharper re-decode. **96 of the 100 files in `SampleImages/` are RAW.** For this corpus,
"zoom in high resolution" currently does almost nothing.

This is also the exact case PRD 1.7 already resolved in RAW's favour. The 96-file
survey found **100% of RAW files carry an embedded JPEG preview at full sensor width**
(`.ARW` 7008×4672, `.CR2` 6000×4000) — which is why RAW zoom is **Tier A**: the
full-resolution pixels are already sitting in the file as ordinary JPEG, needing no
debayer. `Fastcull.Core/Services/RawPreviewDecoder.cs` already finds every embedded
JPEG stream by scanning for SOI/EOI markers.

### B.2 What to do

- **Include RAW in the zoom-tier decode.** `RawPreviewDecoder` currently tries
  candidate streams **smallest-sufficient-first**, which is right for the thumbnail and
  display tiers. Zoom needs the opposite: the **largest** decodable embedded stream.
  Add that path rather than changing the existing ordering, which the other two tiers
  depend on.
- Mind the known `.CR2` case: the largest embedded stream in a `.CR2` is the ~24 MB
  lossless-JPEG *sensor data*, which fails to decode (`Unsupported JPEG data precision 14`).
  That is expected — skip it and take the largest stream that actually decodes. The
  existing decoder already handles this; make sure the largest-first path does too.
- **Tier B, honestly.** If a file's best available stream is below PRD 5.1's
  `FullResIsCheap` 90%-of-sensor-width threshold, there is **no full-resolution path at
  all** — no debayer exists in this codebase (PRD 3.4's documented open gap). Degrade
  exactly as PRD 1.7 describes for Tier B: show the best available tier upscaled, with a
  subtle indicator. **Do not fabricate a full-res path and do not silently show a soft
  image as though it were sharp.** No file in the current corpus should hit this, which
  is itself worth confirming and reporting.

### B.3 1:1 versus fit-to-viewport

The working tree decodes to a `longEdge` sized to the viewport. That is
*higher*-resolution, but it is not what PRD 1.7 specifies: **`Spacebar` toggles 1:1
inspection** — actual pixels, so critical focus can be judged — and PRD 2.2 gives
`Arrow keys` panning with acceleration on hold, with zoom and pan preserved across
navigation.

Move toward the PRD: **decode at full resolution and present at 1:1, with arrow-key
panning.** A 1:1 view without panning is not useful (you would only ever see the centre
of the frame), so panning is part of this task, not a follow-up.

Two consequences to handle explicitly:

- **Arrow keys are mode-dependent.** PRD 2.4 gives the arrows exclusively to carousel
  navigation — but that is filmstrip mode. In zoom mode they pan. PRD 2.2 already calls
  the input layer "an explicit two-state machine, handled in one place at window level".
  Implement it that way: one router, two modes, no scattered key handling.
- **PRD 2.2's `A`/`D` for next/previous-while-zoomed now collides with `A` = rotate
  counter-clockwise.** Resolve it and say what you chose: the sane options are dropping
  `A`/`D` in favour of `PgUp`/`PgDn` (already specified for the same purpose), or
  keeping rotation live in zoom and navigating only by `PgUp`/`PgDn`. Do not leave two
  meanings on one key.
- Rating keys (`1`–`5`, `Z`, `X`, `C`) stay live while zoomed, per PRD 2.2.

### B.4 Memory — the part most likely to bite

A full-resolution 7008×4672 frame is roughly **131 MB** as BGRA8. This app already
fails its 4 GB peak-working-set budget at 5.25 GB, because `FilmstripItemViewModel`
retains every decoded thumbnail and display image and **nothing evicts them** — PRD
3.3's LRU cache has never been built. Zoom adds the largest single allocations in the
app on top of that.

Non-negotiable:

- **Exactly one zoom-tier image resident at a time.** Releasing on zoom exit and on
  changing the zoomed photo is already what `ReleaseZoomImage()` is for — make sure
  both paths always fire, including when zoom is exited by navigating rather than by a
  key.
- **Never dispose a `SoftwareBitmap` that has been handed to `SetBitmapAsync`.** Drop
  the managed reference and let it be reclaimed. This project fail-fasted the process
  once (`0xC000027B`, `AsyncCopyToSurfaceTask::CopyOperation`) doing exactly that; the
  comment block in `FilmstripItemViewModel` documents it. Releasing the zoom image is a
  new call site for the same hazard.
- **Cancellation must actually cancel.** Navigating away from a zoomed photo mid-decode
  must cancel the job, not orphan it. The `_zoomCts` plumbing exists — verify it under a
  fast navigate-while-decoding test, not by inspection.
- **Add a dimension guard.** PRD 3.3 specifies capping any image whose decoded size
  would exceed 512 MB (~128 MP at RGBA) to a downscaled decode with a notice. That guard
  was scoped into the unrun followup4 task, and zoom is precisely the feature that makes
  its absence dangerous — a single large stitched panorama at full resolution can take
  the app down. Implement the minimal version here, and note in the report that it
  overlaps followup4's scope so that task can drop it.

### B.5 Verify

- Zoom, pan to a corner, navigate to the next photo, come back: no crash, no leak, no

  the same discipline the harness already applies to the cache-hit row.
